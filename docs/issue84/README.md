# Issue #84 — 복수 종과 확인된 제보자 집계

시작 main: `7eee77350514eb9686e59bbab4f1ad7d821439fb`. PR 직전 최신 main `884c4d5787df1bab3f851ff51d9aec7ca2a7b5e0`의 자동 갱신 변경을 대조했다. 운영 D1 쓰기·Worker/Pages 배포·main 병합은 수행하지 않았다.

## 종 분리

- `동박새3 찌르레기2 까치5`, `동박새 3 찌르레기 2 까치 5`, 쉼표 입력은 모두 1건·3종·10개체다.
- 공식 국명으로 **전체 문자열의 유일한 해석**이 가능한 경우에만 공백을 구분자로 해석한다. 영명·학명은 기존의 한 종 입력 규칙을 유지한다. 불완전한 접두사 추출, 추측 보정, 잘못된 수량 보정은 없다.
- 신규 접수는 기존 raw_submissions에 원문을 저장하고 기존 sightings에 종별 값을 저장한다. 과거 읽기는 reports.species를 바꾸지 않는다. 기존 구조화 식별값은 우선한다.
- 동일 종이 두 번이면 고유종수는 1종, 수량은 불확실이다. 같은 수량 토큰이 반복되어도 임의 삭제·합산하지 않는다. 미입력은 null이고 0·1로 대체하지 않는다. 과거 0 입력은 불확실로 남긴다.
- 공개 지도·검색·회원 종 목록·누적종수·관리자 통계·종별 관리자 조회가 같은 해석을 사용한다. 보호종과 번식·위치 가림 판정도 공백 복수 종을 확인한다. 과거 비번식 확인은 당시의 구분자 정규화 결과와 원문 좌표·관찰일·메모가 정확히 일치하는 경우 유지하며, 종/좌표/날짜/메모 변경과 잘못된 원문은 확인 근거로 인정하지 않는다.

## 동일인 확인: 자동 이름 연결 없음

현재 제보에는 신원을 검증하는 회원 ID가 없으므로 **관리자가 본인 확인을 마친 명시적 제보 ID 집합**을 기록한다. 공백 제거, 유사 이름, IP 해시로 확인하거나 자동 연결하지 않는다. 같은 닉네임으로 새 제보가 들어와도 확인 그룹에 자동 가입시키지 않는다.

- 추가 migration: `reports-api/migrations/0007_reporter_identity.sql`. 기존 reports/raw_submissions/checklists/sightings/승인/개체수/동의/좌표는 수정하지 않는다.
- 확인 기능은 기본 OFF다. 별도 운영 승인 후 migration을 검증·적용하고 두 Worker의 `REPORTS_CONFIRMED_IDENTITIES=1`과 `REPORTS_PUBLICATION_REQUIRED=true`를 함께 설정해야 한다. 이 PR은 배포 설정을 바꾸지 않는다.
- 확인·해제는 기존 Access 인증과 쓰기 gate 뒤의 `POST /admin/api/reporter-identities`를 사용한다. 확인 시 제보 ID와 근거를 다시 DB 트랜잭션 안에서 검증한다. 누락·익명·중복·다른 활성 그룹과 겹치는 제보는 거절한다.
- 최초 닉네임은 선택한 제보의 received_at 오름차순, 동률이면 ID 오름차순의 최초 기록을 기준으로 한다. observed_on(과거 관찰일)로 최초 가입을 추정하지 않는다.
- 공개 집계는 각 행의 approved + name_public=1을 유지한다. 최초 기록이 비공개·승인 취소·삭제되면 최초 이름을 다른 행을 통해 공개하지 않고 각 원래 공개 이름으로 돌아간다.
- 공개 이력은 원래 닉네임을 보존한다. 그 이력 ID가 witness인 요청은 확인된 그룹의 누적 고유종수를 제공한다. 월간/전체 기여자는 공개 가능한 최초 이름을 표시한다.
- 서로 다른 그룹/미연결 기록의 공개 표시명이 같으면 전체·월간 출처의 회원 통계는 404로 닫는다. 이력 ID가 있는 출처는 정확한 그룹으로 조회한다. 사람을 추측해서 합산하지 않는다.
- 관리자 통계는 확인한 그룹을 집계하되 원본 제보 조회는 원문을 유지한다. 기존 확인·해제 기록은 인증된 `GET /admin/api/reporter-identities`로 조회한다(최근 그룹 최대 200, 이벤트 최대 400).
- 추가 관리자 화면 버튼은 없다. 이 단계의 확인 인터페이스는 인증된 API이며 근거를 사람이 검토한 뒤 호출한다.

확인 요청 형식(합성 ID):

```json
{"action":"confirm","reportIds":["synthetic-a","synthetic-b","synthetic-c"],"confirmedSamePerson":true,"reason":"본인 확인 경로와 검토 근거"}
```

해제 요청:

```json
{"action":"revoke","groupId":"확인 응답의 UUID","reason":"해제 근거"}
```

## 이력·공개 상태·복구

확인 그룹은 수정/삭제할 수 없고 active=1에서 0으로 한 번만 해제한다. 확인자·근거·시각과 해제자·근거·시각, append-only 이벤트를 보존한다. 잘못된 확인은 그룹 해제 후 새 ID 집합을 재확인한다. 대표 제보의 외래키는 두지 않아 기존 제보 삭제를 막지 않는다.

확인·해제는 기존 writer claim과 freeze를 통과한 원자적 쓰기다. 같은 트랜잭션에서 publication revision이 증가한다. 공개 읽기는 기존 publication/witness/primary batch 검증에 더해 identity 보호 트리거 존재를 같은 스냅샷에서 확인한다. 그룹/별칭/근거/관리자 정보/정확 좌표는 공개 통계 응답에 추가하지 않는다.

운영 반영은 별도 승인 대상이다. 승인 전후 읽기 대조 → 로컬/스테이징 migration·확인·해제 재연 → 스냅샷/복구 계획 확인 → 사용자 승인 → 적용 순서를 지킨다. 문제가 있으면 그룹 해제 또는 기능 스위치 OFF로 기존 정확 닉네임 집계를 복원한다. 원문 복구를 위한 역 UPDATE는 필요 없다. 운영에서 이 절차를 실행하지 않았다.
