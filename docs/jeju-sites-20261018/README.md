## 4. 변경 범위와 호환성

- `index.html`: 기존 concat 배열 끝에 206·207 추가. 공통 프로필·추천·보호 함수 본문은 동일. 제목의 202곳 표시와 추가 안내, 좌표 설명 문구 2줄만 함께 조정.
- `weather-proxy/src/sites.js`: 두 ID의 이름·좌표·환경·선상 여부 추가. **202곳 전부** 런타임과 일치하며 좌표·이름·환경·선상 불일치가 없다.
- `data/jeju-birding-sites-20261018.json`: 접근점 출처, 조류·접근 근거, 자료 시점, 제한, 중복·보류 판단과 기존 엑셀 해시 보관. 런타임의 기존 필드 구조를 그대로 사용.
- 기존 공유 생성기로 신규 `share/206`, `share/207` HTML과 카드만 생성. 검증된 대표종이 각각 1종이므로 기존 SEO의 최소 3종 조건을 유지해 개별 검색용 페이지는 만들지 않음. 기존 SEO·sitemap·공유물 내용은 동일.
- 개수 고정 회귀시험과 Chrome 시험의 200 조건을 202에 맞춤. 기존 190개와 중부 10개의 전체 필드 검사는 유지. 신규 데이터·계절·기상 결측·등록 계획과 SQL 실패 조건 시험 추가. CI에 새 Python 시험 포함.
- 별도 운영 추가용 SQL은 기존 200개 전체 스냅샷·고유 ID·NORMAL 상태·generation 일치 및 새 206·207만 허용하도록 준비. 과거 중부권 SQL이나 운영 전환 도구의 기본 190 보호 조건은 수정하지 않음.

좌표는 공식 접근점 수치를 보정 없이 사용했다. 각 후보의 원자료→런타임→Worker→카카오맵→Windy가 일치하며 네이버는 접근점 명칭 검색이다. 저장된 Hotspot ID가 없으므로 eBird 링크를 추측하지 않았다. 두 곳은 육상 방문이므로 KSA·선상·섬 상륙 경로를 추가하지 않았다. 조석은 두 곳 모두 비활성화하고 관측소를 임의 연결하지 않았다. 북촌은 파고 확인을 필수로 한다.

### 추천 엔진에서 확인한 한계

1. **천지연은 겨울(11~2월) 자동 추천에서 제외한다(2026-10-18 운영 정책 결정).** 기존 겨울 분류에서 `unclassified`이며 엔진은 수정하지 않았다. 지도 검색·필터·마커·상세 정보는 정상 표시한다. 시험 `제주 신규 겨울 분류`가 이 제외를 고정한다.
2. **프로필의 겨울 시기와 자동 추천의 허용 계절은 다르다.** 동일한 유효 합성 기상에서 1월은 북촌, 4월은 없음, 7월·10월은 두 곳이 기존 엔진의 일반 후보로 허용됨을 시험했다. 여름·가을 출현을 입증했다는 뜻이 아니다. 계절에 따른 엄격한 후보 제외를 원한다면 기존 추천 정책까지 검토하는 별도 변경이 필요하다.
3. 자동 기상 파일은 기존 200곳 자료를 그대로 보존했다. 신규 2곳은 저장 기상이 없으므로 현재 추천에서 제외된다. 전체 202곳에 대한 실제 기상 생성 성공을 확인했다는 보고는 하지 않는다. 생성기·프론트의 결측 안전 경로를 모의 자료로 시험했다.

### 민감종 보호

실시간 출현점·둥지·번식 좌표와 관찰 제보는 추가하지 않았다. 기존 위치 가림·승인·철회·공개 권한·GPS 보호 코드와 제보 API는 그대로다. 새 데이터의 `rare/mijo/recommend5`는 모두 false이며 임의 별점도 넣지 않았다. 공개 접근점과 과거 기록을 명확히 구분하고 민감한 세부 지점으로 유도하는 링크를 추가하지 않았다.

## 6. 운영 반영 전 조건 — 현재 미실행

이 검토본은 운영 반영 승인을 요청하기 위한 검토 자료이며, 운영 반영 완료본이 아니다. 승인 전 push·merge·deploy·운영 D1 실행은 하지 않는다.

승인 이후에도 최신 main·기존 레코드 보존·현장 접근 공지를 다시 확인하고, 원래 생성기로 **202곳 전체 기상자료를 정상 생성하여 원본 validator를 통과**해야 한다. 현재 보존된 200곳 기상 파일을 202곳으로 검증하면 ID 불일치로 거부되는 것이 정상이다. 시간 계약 시험에서는 과거 배치의 ID만 모의 주입하고, 전체 202곳에 대해서는 거부가 유지됨을 별도 시험했다. validator 본문은 완화하지 않았다.

제보 장소 registry는 런타임과 별도다. 운영 D1의 현재 개수를 조회하지 않았으므로 200개라고 단정하지 않는다. 승인 후 `sites`와 `system_state`를 읽기 전용으로 확인하고 `prepareSiteSeed(..., {expectedCount:202})`로 계획을 만든다. 실제 기존 스냅샷과 SQL 전제가 다르면 즉시 중단한다. 190개라면 이 200→202 SQL을 실행하지 않는다. SQLite 검증 외에 native local D1도 검증한 뒤, 새 ID 206·207만 추가하고 기존 레코드 해시·외래키·관찰 제보 불변을 확인해야 한다.

기상 Worker의 사이트 목록 반영과 Pages 반영은 승인된 순서로 수행하고 기존 설정·비밀키를 보존한다. 제보 Worker나 보호 로직의 배포는 이 데이터 확장에 필요하지 않다. 모든 운영 단계는 별도 승인 대상이다.

현재 남은 불확실성은 당일 통제·북촌 주차/화장실 현황, 과거 조류 기록과 현재 출현의 차이, 추천 계절 정책, 실제 202곳 기상 생성 및 별도 운영 registry 상태이다. 이를 확인 완료로 표시하지 않았다.
