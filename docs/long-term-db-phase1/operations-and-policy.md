# 데이터 표준 v1.1 — Phase 1 접수 정책과 전환 운영 설계

상태: 검토용 설계 초안. 이 문서의 migration SQL·운영 전환 단계는 실행하지 않았다. export, restore, migration, Worker 배포를 수행하지 않았다. 상세 데이터 수치는 사용자가 제공한 Phase 0 기준선이다. 재개 후 인증 세션 갱신을 거쳐 기본 건수·상태·sqlite_schema와 Worker 배포 메타데이터만 읽기 전용 재확인했다. 그 실행 시각·범위·무변경 증거는 execution-evidence.md에 별도로 기록하며 실제 적용 직전에 다시 측정해야 한다.

테이블·컬럼의 최종 정의는 함께 작성한 스키마 초안을 따른다. 도메인 10개 테이블 외에 전환 제어용 `migration_control`(단일 epoch/mode), `mutation_permits`(요청별 허용 변경), `migration_assertions`(CHECK 기반 transaction 검증)를 제안한다. purge tombstone은 필요한 운영 개념이며 비민감 보관 위치·독립 복구 수단을 확정해야 한다. 보호장치가 구현·검증되지 않은 상태에서 쓰기 전환을 진행하지 않는다.

## 1. 확정 정책과 보존 경계

번식 관련 관찰은 수집 대상에서 제외한다. 둥지·번식지·알·포란·육추·둥지 주변 번식행동·번식 위치를 특정할 수 있는 관찰은 일반 관찰 DB에 편입하지 않는다. 별도의 `breeding_sensitive` 등급이나 좌표를 흐린 번식 기록을 만들지 않는다.

신규 접수의 `non_breeding_confirmed=1`은 **사용자가 안내문에 명시적으로 확인했다는 사실**이다. 번식 관련이 아님을 서버가 생물학적으로 입증했다는 뜻이 아니다. 종명·희귀 여부·보호 등급·계절·월만으로 번식 여부나 비공개 여부를 추정하지 않는다.

기존 21건은 확인 정보가 없으므로 `non_breeding_confirmed=NULL`로 남긴다. 이를 거짓, 참, 위반으로 변환하지 않는다. 승인 17건·반려 4건을 모두 보존하며, 종명·좌표·개체수·시각·동의의 기존 값을 자동 수정하지 않는다. legacy 자료의 정상적인 관리자 수정도 과거의 사용자 확인을 만들어내지 않는다.

raw는 정상적인 검토·승인·수정 과정에서 불변이다. 단, 저장 후 금지정보임이 확인된 경우에는 아래의 **예외 삭제 절차**가 불변 원칙보다 우선한다. 금지 원문을 감사용이라는 이유로 다른 테이블에 복사해 장기 보존하지 않는다.

## 2. 신규 제보 입력 흐름

1. 안내문을 표시한다: “이 제보는 둥지·포란·육추·번식지 등 번식 관련 관찰이 아닙니다.” 체크박스는 기본 미선택이며 사용자 동작만으로 선택한다.
2. 화면은 명시적 확인, 적용 정책 버전, 요청 식별자와 기존 입력을 전송한다. 서버가 확인값을 기본 `true`로 채우는 호환 처리는 금지한다.
3. 서버는 본문 크기·JSON 구조·허용 필드·정확한 boolean 값을 먼저 검사한다. 확인 누락·`false`·문자열 `"true"` 등은 저장 전에 거부한다. 정책 버전이 지원되지 않으면 새 화면을 요구한다.
4. 실패 본문을 raw, 오류 로그, 분석 이벤트, 재시도 큐에 쓰지 않는다. 오류 응답에도 종·좌표·메모 원문을 되돌려 넣지 않는다. 필요한 운영 지표는 오류 코드와 집계값만 남긴다.
5. 확인 후에도 길이·날짜·좌표 쌍·종·개체수, Turnstile, 제출 횟수 제한을 검증한다. 사용자 확인 자체가 일반 입력 검증을 대체하지 않는다.
6. 사용자가 수집 제외 대상임을 직접 선택했거나 필수 확인을 하지 않았다면 저장 전에 거부한다. 종명·본문·이미지·월·계절의 AI 분석이나 키워드·규칙으로 번식 가능성을 추정해 자동 차단하지 않는다. 저장 후 관리자가 실제 금지자료임을 확인한 경우에만 제5절의 예외 폐기를 진행한다.
7. 수락한 생태 관찰 입력 필드의 **정규화 전 값**과 확인 사실을 raw에 기록한다. raw의 의미는 ‘수락한 최초 입력 필드’이며 HTTP 요청 바이트 전체가 아니다. 인증 헤더·Turnstile 토큰·원본 IP·쿠키는 포함하지 않는다. 임의의 추가 필드는 거부해 숨겨진 본문을 보존하지 않는다.
8. 정규화 결과를 checklist와 sightings로 만들고, 호환 기간에는 같은 D1 transaction에 기존 `reports` 행을 함께 쓴다. 성공 확정 후에만 접수 번호와 기존 형식의 응답을 반환한다.

새로 저장되는 pending 자료를 일반 승인 관찰로 취급하지 않는다. 확정 정책에 맞는지 검토하기 전 공개 범위는 제6절의 명시적인 공개 결정에 따른다. 악의적 허위 확인이나 이미지 속 내용을 체크박스만으로 완전히 차단할 수 있다고 보장하지 않는다.

## 3. 기존 POST 계약과 필수 확인의 전환

현재 `POST /reports`에는 위 확인 필드가 없다. ‘확인 없는 요청을 모두 거부’와 ‘기존 본문을 그대로 영구 수락’은 동시에 만족할 수 없다. GET 응답과 정상 수락 응답은 유지하되, **확인 누락 요청의 거부를 의도적인 입력 계약 강화**로 문서화한다.

안전한 순서는 다음과 같다.

| 단계 | 화면·서버 동작 | 통과 조건 |
|---|---|---|
| 준비 | 새 정책을 아직 적용했다고 표시하지 않는다. 정책 인식 서버·DB guard·새 화면을 비운영 환경에서 검증 | 누락·false·직접 요청을 포함한 차단 시험 통과 |
| 화면 준비 | 새 화면에 안내·기본 미선택 확인·정책 버전 포함. 입력을 캐시에 자동 보관하지 않음 | 서버가 추가 필드를 무시하는 구버전이어도 화면 오작동 없음 |
| 서버 전환 | 새 서버가 모든 신규 접수에서 명시 확인을 필수화. DB guard 활성화와 구버전 writer 차단을 일관되게 수행 | 예전 브라우저·구버전 Worker가 확인 없이 성공할 수 없음 |
| 후속 안내 | 구화면 제출에는 안정적인 오류 코드와 새로고침 안내를 제공 | 사용자가 입력을 확인하고 다시 제출할 수 있음 |
| 유지 | 동일 URL과 수락 응답의 기존 필드를 유지 | 기존 지도·상태 조회·관리자 흐름 회귀 시험 통과 |

구화면에 서버가 임의 확인을 덧붙이거나, 이행 기간이라는 이유로 정책 발효 뒤 확인 없는 요청을 저장하지 않는다. 새 서버가 먼저 활성화되면 구화면 제출이 잠시 거부될 수 있다. 운영자는 정책 발효 시각, 화면 캐시 갱신, 재제출 안내를 승인해야 한다. 읽기 서비스 무중단과 오래된 입력 본문의 무조건 수락을 같은 의미로 약속하지 않는다.

정책 발효 전의 기존 시스템을 최신 정책 준수 상태라고 부르지 않는다. 운영 배포 순서가 이 경계를 보장하지 못하면 접수 쓰기를 잠시 닫고, 공개 조회는 유지하는 제한된 전환을 선택한다.

## 4. 전체 탐조 checklist 흐름

한 번의 탐조를 한 checklist로 입력하고 그 아래에 여러 sightings를 둔다. 관찰일, 시작 시각, 지속 시간, 거리, 관찰자 수, protocol, complete_list는 사용자가 실제로 입력·확인한 정보만 기록한다. 시작 시각의 시간대도 명시한다. 빈 값을 0, 한 명, 일정 시간, `complete_list=true`로 채우지 않는다.

각 sighting은 종명 원문과 검증된 분류군 연결을 분리한다. count_value와 count_accuracy도 별도 입력으로 받는다. 수량을 입력했다는 이유로 추정치인지 정확한 수량인지 단정하지 않는다. 미상은 NULL이며, 0은 명시적 관측·프로토콜 의미가 정의된 경우에만 허용한다. 전체 목록 확인을 근거로 입력하지 않은 종의 0건 행을 자동 생성하지 않는다.

전체 탐조 기록에도 같은 수집 제외 확인을 적용한다. 어느 일부가 금지정보임을 확인한 경우 전체 원문과 첨부에 그 정보가 포함될 수 있으므로 해당 제출 단위의 처리 범위를 먼저 판정한다. 금지 부분을 지우고 원본인 것처럼 다시 저장하는 자동 정제는 하지 않는다. 정상 관찰을 별도로 보존하려면 사용자가 금지정보 없는 새 제출을 명시적으로 제공하도록 한다.

**기존 reports로 되돌릴 수 있어야 하는 기간에는 상세 checklist 기능을 공개하지 않는다.** 종별 서로 다른 개체수, effort, 여러 관찰자, 미디어, 기존 구조가 표현할 수 없는 공개 상태를 reports 한 행으로 손실 없이 투영할 수 없기 때문이다. 스키마 지원과 기능 출시 시점을 분리한다. 기존 POST의 표현 범위를 넘어서는 신규 API는 legacy 복귀 기간 종료 후 별도 출시한다.

## 5. 관리자 검토와 금지정보 예외 삭제

정상 검토는 pending → approved/rejected, approved → unpublished, 수정 후 재승인 등의 실제 행위를 append-only reviews에 기록한다. 입력자·수정자·검토자와 시각을 구분한다. 현재 상태 변경, reports 호환값, reviews, audit_log는 한 transaction으로 확정한다. raw를 수정하거나 존재하지 않는 과거 이벤트를 채우지 않는다. 일반 감사의 before/after는 허용 필드만 기록한다. 좌표·이름 등 민감한 값의 변경을 별도 보안 버전 참조로 남기는 설계를 선택할 경우, 참조 대상도 불변 버전이어야 하며 단순히 현재 행 ID만 기록하고 변경값이 복원 가능하다고 설명하지 않는다.

legacy의 현재 status·decided_at·admin_note는 가져온 상태 정보로 보존한다. 이를 과거 submitted/approved 이벤트들로 재구성하지 않는다. migration 자체의 실행 기록은 schema_migrations에 남기며, 가상의 사용자·관리자 과거 audit를 만들지 않는다.

관리자가 번식 관련 금지정보라고 확인한 경우에는 단순 `rejected` 보관이나 좌표 흐림으로 종결하지 않는다. 일반 반려와 다음 절차를 구분한다.

1. 권한 있는 관리자만 사유 코드로 예외 삭제를 시작한다. 민감한 설명을 자유형 관리자 메모에 다시 적지 않는다. 수집 제외가 확인됐다는 판단은 기록하되 위치·종·번식 내용은 감사기록에 남기지 않는다.
2. 즉시 공개·검색·연결·첨부 접근을 중단한다. `reports`를 읽는 복귀 경로도 같은 차단을 적용해야 한다. 공개 캐시의 명시적 무효화와 최대 TTL 경과 확인을 포함한다.
3. DB 안의 raw 원문, legacy snapshot, reports, checklist/sightings, 민감 필드를 포함한 reviews와 audit의 before_json/after_json, 관련 환경자료·위치·검색 색인을 삭제 범위에 넣는다. 정상적인 공유 taxa/sites는 삭제하지 않는다.
4. 다른 정상 관찰이 삭제 대상의 `spot_key`를 가리키면 자동으로 새로운 공개 점을 만들지 않는다. 해당 연결을 비공개 상태로 전환한 후 명시적으로 재연결·해제하도록 검토한다. 연결 해제로 실제 좌표가 갑자기 공개되지 않아야 한다.
5. DB 데이터는 한 transaction으로 제거한다. RESTRICT 외래키는 명시한 자식→부모 삭제 순서로 만족시킨다. 일반 UPDATE/DELETE 차단 trigger에는 인증된 purge 실행만 허용하는 별도 경로가 필요하다. guard를 통째로 끄거나 raw 불변 trigger를 임시 제거하는 절차를 정상 운영 API로 만들지 않는다.
6. 실제 미디어, 썸네일, 변환본, EXIF, 업로드 임시본, 저장소 버전, 미처리 큐, 추출 텍스트, 실행 로그, export 사본의 삭제·만료까지 추적한다. 객체 저장소와 D1은 하나의 원자적 transaction이 아니므로 접근 차단 → 삭제 재시도 → 완료 확인으로 처리한다. 삭제 재시도 표식에는 원문을 넣지 않는다.
7. 비민감한 삭제 증빙만 남긴다: 불투명 대상 ID, `excluded_content_purged` 같은 사유 코드, 권한자 ID, 요청 ID, 시작·완료 시각, 처리 대상별 완료 상태. 종명·좌표·관찰일·제보자명·자유 메모·본문/파일 체크섬은 남기지 않는다. 작은 후보 공간의 해시도 내용 추론을 도울 수 있으므로 감사용으로 보존하지 않는다.

이 절차는 ‘일반 경로 raw 불변’의 명시적 예외이다. 비민감 tombstone 또는 별도 삭제 관리 기록은 관찰 자료가 아니며, 어떤 테이블에 둘지는 스키마와 권한 설계에서 확정한다. 감사 테이블이 일반적으로 append-only여도 금지정보가 실수로 들어간 과거 audit payload를 영구 보존하라는 뜻은 아니다.

기존 21건의 번식 여부를 migration에서 조사 없이 추정해 삭제하지 않는다. 향후 실제 검토에서 금지정보가 확인됐을 때만 승인된 정책·권한에 따라 위 절차를 적용한다.

### 백업의 삭제 한계

D1 Time Travel은 자동 활성화되어 과거 상태를 보존하며, 문서상 Free 7일/Paid 30일 범위가 적용된다. 현재 행을 DELETE했다고 과거 bookmark의 사본까지 즉시 지웠다고 말할 수 없다. 공식 문서에는 여기서 사용할 수 있는 개별 행별 Time Travel 제거 기능이 제시되어 있지 않다. [Cloudflare Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)

따라서 운영자는 금지정보 발견 시 서비스·일반 DB에서 즉시 제거하는 기한과 공급자 복구 기록의 최대 잔존 기간을 구분해서 결정해야 한다. 모든 사본에서 즉시 물리 제거가 필수라면 현 D1 Time Travel 구조로 그것을 입증할 수 없으므로 출시 전 공급자 확인 또는 다른 저장 구조 검토가 필요하다.

별도 권한으로 보호하는 비민감 삭제 tombstone 목록을 복구 대상 DB와 독립적으로 보존해야, 과거 복구로 삭제 사실까지 사라지는 것을 막을 수 있다. 복구 후 공개·접수를 재개하기 전에 이 목록으로 삭제를 재적용하고 객체·캐시 접근을 다시 검사한다. 원문을 포함하는 로그·외부 사본의 보존 기간과 삭제 권한이 정해지기 전에는 ‘삭제 완료’를 선언하지 않는다.

## 6. 좌표 저장과 공개 결정

| 개념 | 의미 | 처리 원칙 |
|---|---|---|
| 실제 좌표 | 실제 관찰 위치 | 기존 값을 그대로 이전. 정상 비번식 관찰은 원칙적으로 실제 위치 공개 가능 |
| 대략 좌표 | 기존 승인 전 황색 마커의 위치 | 저장된 값 보존. 재조회 때 재생성하지 않음. 번식자료 저장 수단으로 사용하지 않음 |
| 별도 공개 좌표 | 관리자가 선택한 공개 위치 | 두 좌표가 함께 있는 값. 실제 좌표와 의미를 분리 |
| 공개 정책 | 실제/별도/비공개 등 공개 결정 | 좌표 NULL 여부 자체와 구분. pending 여부·이름 동의와도 구분 |
| 지점 연결 | spot_key로 가리키는 표시 기준 | 실제 관찰 위치와 별개. 연결이 원자료 위치를 덮어쓰지 않음 |

기존 API 어댑터는 legacy의 `public_lat ?? lat`, `public_lon ?? lon` 동작을 재현한다. 사용자 제공 기준선에서는 승인 17건 모두 별도 공개 좌표가 없고 실제 위치가 공개된다. 이번 설계에서 이를 자동으로 흐리거나 비공개로 바꾸지 않는다. 신규 모델에서는 좌표 쌍 CHECK와 명시적인 공개 정책을 사용하고, 잘못된 공개 정책/좌표 조합이면 공개하지 않으며 오류를 보고한다.

현재 코드 `shared.js`의 `SENSITIVE_SPECIES` 목록은 종명만으로 승인 전 공개를 보류한다. 확정된 신규 정책을 적용하는 writer에서는 이 목록을 번식 판정이나 종별 자동 비공개 기준으로 재사용하지 않는다. 기존 `pending_public` 원값은 그대로 보존한다. 신규 pending 공개 정책은 모든 종에 동일한 절차로 적용하며, 사용자가 확정한 정상 관찰의 실제 좌표 공개 원칙은 승인 후 흐름에서 유지한다.

승인 15건의 `pending_public=1`은 원값을 보존한다. 공개 대기 여부는 status와 결합해 계산해야 하며 이 잔류값만으로 다시 황색 마커를 만들지 않는다. `name_public`도 접수 당시 값과 현재 이름 공개 결정을 구분한다. 동의가 없으면 이름을 응답·검색·사진 크레딧으로 우회 공개하지 않는다.

`spot_key=NULL`은 자기 점, `fixed:<siteId>:<n>`은 수동 점, UUID는 다른 제보의 점이라는 namespace를 유지한다. 혼합 namespace이므로 sites 외래키 하나로 바꾸지 않는다. 신규 링크는 대상 존재·자기 연결·순환·다단 연결·고정 점 존재를 검사한다. 현 승인 상태를 벗어난 대상에 연결된 이력의 표시 결과도 검사한다. 기존 GET 호환 어댑터의 표시 방식과 관리자가 새로 허용할 링크 규칙은 별도로 정의한다.

## 7. dual-write 선택과 D1 transaction

| 방식 | 장점 | 제한·선택 |
|---|---|---|
| 앱의 순차 별도 쓰기 | 단순함 | 첫 쓰기 성공 뒤 둘째 실패로 분리됨. 채택하지 않음 |
| 같은 D1의 앱 batch | 입력 검증·정규화·리뷰·동의를 한곳에서 다룸 | 모든 writer의 경로 통제가 필요. 권장 본체 |
| DB trigger로 전체 변환 | 구 Worker/직접 SQL도 감지 가능 | 원래 입력·행위자·사용자 확인을 알 수 없음. 종 분리와 정책 로직 중복 위험 |
| 앱 batch + 제한된 DB guard | 풍부한 앱 판단과 우회 쓰기 차단 결합 | gate/permit과 모든 동작 시험이 필요. 권장 최종 구성 |

D1 `batch()`는 같은 DB에 보낸 문장들을 transaction으로 처리하고 문장 실패 시 전체 묶음을 롤백한다. 서로 다른 DB나 객체 저장소 사이의 원자성은 보장하지 않는다. [D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)

권장 mutation의 논리 순서는 다음과 같다. 실제 DDL/실행 코드는 Phase 2에서 검증하며, 이번 단계에서는 실행하지 않는다.

1. 요청 ID의 재실행 여부와 요청 의미가 같은지 검사한다. 같은 ID·같은 요청은 기존 결과, 같은 ID·다른 내용은 충돌로 처리한다. 기존 dedupe_hash와 요청 idempotency key를 같은 개념으로 사용하지 않는다.
2. 현재 정책 epoch, 쓰기 모드, 대상 revision을 읽어 계산한다. 레코드의 이전 값을 사용하는 승인은 관리자 조회 시 revision도 함께 받아 오래된 화면의 덮어쓰기를 방지한다.
3. 하나의 batch 안에서 gate/epoch와 expected revision을 compare-and-swap으로 확인하고 mutation permit을 연다.
4. raw 최초 입력, reports 호환 행, checklist/sightings, 해당 review/audit를 같은 batch로 확정한다. 수정 시 raw는 건드리지 않는다.
5. 입력 예상치·결과 행 수·연관 행 존재·revision 증가를 transaction 내부에서 검증하고 permit을 닫는다. 필요하면 checkpoint와 처리 결과를 같은 묶음에 기록한다.
6. batch 성공 이후에만 클라이언트에 성공을 응답한다. 실패는 전체 재시도하며 불명확한 응답도 같은 요청 ID로 조회/재시도한다.

**CAS UPDATE가 0행을 변경해도 SQL 오류는 아니다.** batch가 끝난 뒤 `changes=0`을 발견하는 것만으로 이미 커밋된 다른 쓰기를 되돌릴 수 없다. 불일치 시 transaction 안에서 CHECK 또는 `RAISE(ABORT)` 같은 검증 실패가 발생하도록 설계해야 한다. 마지막 무결성 검증도 0행 SELECT 결과를 응용 코드에서 보는 데 그치지 않아야 한다.

### 구 Worker·직접 SQL의 우회 방지

gate 값을 새 앱만 읽으면 구 Worker나 직접 SQL은 그 값을 무시할 수 있다. 따라서 배포 버전 확인과 ‘운영자가 직접 SQL을 안 쓸 것’만으로 완전한 동기화를 보장하지 않는다.

Phase 2 보호장치의 최소 요건은 다음과 같다.

- reports의 INSERT/UPDATE/DELETE에 좁은 guard를 둔다. 허용된 transaction 내의 mutation임을 입증하지 못하면 차단한다.
- `mutation_permits`의 permit은 대상 ID, 동작, 기존 reports 22개 필드의 before/after JSON, 정책 epoch에 묶고 NULL과 값의 형식까지 일치시킨다. INSERT는 확인값 1을 요구한다. `migration_control` mode는 `reports_only`/`pair` 등 확정된 상태만 허용하며, 전체 DB 쓰기를 잠시 허용하는 전역 boolean을 열어두지 않는다.
- 새 앱은 permit 생성→데이터 쓰기→AFTER trigger의 permit 소비를 **같은 batch**에서 수행한다. 신규 스키마의 대응 행·값은 같은 batch 마지막 `migration_assertions` 검증으로 검사한다. permit이 커밋 후 열린 채 남지 않게 제약과 최종 검증을 둔다. 실패하면 permit 생성·소비도 함께 롤백한다.
- 행위자·정책 확인·전체 새 값이 없는 구 Worker의 단독 UPDATE는 실패해야 한다. INSERT뿐 아니라 승인·반려·공개취소·동의·좌표 수정·탐조지 연결·spot 연결·해제 모두 포함한다.
- 제어 테이블/trigger를 바꿀 수 있는 DB 소유자까지 DB 자체로 완전히 막는다고 주장하지 않는다. 생산 DML 권한은 최소화하고, 승인된 관리 도구도 동일 mutation 경로를 사용한다.

기존 Worker 동시 실행·진행 중 요청의 경계도 비운영 환경에서 시험한다. 쓰기 보호 활성화 시 구요청이 실패할 수 있으므로 안정적인 오류·재시도 경로가 필요하다. 인증 정보나 관리자 사용자명은 permit·로그에 불필요하게 중복 보존하지 않는다.

이 gate/guard 설계가 SQL 초안에 완전히 구현되지 않았다면 그 부분은 **Phase 2 쓰기 전환을 막는 미완성 항목**이다. 데이터 모델 DDL만 실행하고 dual-write 안전성이 확보됐다고 판정하지 않는다.

## 8. backfill과 실행 중 변경의 경합

received_at은 관리자 수정 시 바뀌지 않으므로 증분 복사의 커서로 사용할 수 없다. status·species·좌표·연결·동의의 변경도 포착해야 한다. 단순히 기존 21건을 읽고 나중에 upsert하는 방식은 중간에 승인된 값을 오래된 snapshot으로 덮어쓸 수 있다.

권장 순서는 **새 정책과 mutation 경로 준비 → 모든 writer의 guard 적용 → 신규 쓰기 atomic dual-write → 기존 행 backfill**이다. Phase 0의 행 수가 작아도 경합을 무시하지 않는다.

각 legacy 행의 backfill은 다음과 같이 수행한다.

1. 기존 UUID로 안정적인 대상 ID를 정한다. 하위 sighting ID는 legacy:<UUID>:1로 결정적으로 생성한다. 서로 다른 reports 행을 합치지 않는다.
2. 모든 기존 필드를 읽고 단일 종/다종 미해석/판단 불가를 구분한 sighting 1개 이전 계획을 만든다. 다종 원문은 자동 분할하지 않는다. 기존 revision이 없다면 필드 전체의 NULL을 구별한 비교값을 준비한다. 서버 해시만 계산하고 실제 행과 비교하지 않는 계획은 부족하다.
3. 한 batch 안에서 gate와 **현재 reports 행이 읽었던 상태와 같은지** 검증한다. 변경됐으면 transaction을 실패시켜 최신값을 다시 읽는다. SQL 내부 INSERT…SELECT로 동일 현재 행을 읽고, 앱에서 준비한 단일/미해석 판정이 정확히 그 원문에 대한 판정인지 확인한다.
4. legacy snapshot 원자료는 `legacy_reports_snapshot`으로 한 번 저장한다. 이를 최초 제출 JSON이라고 부르지 않는다.
5. 아직 없는 checklist/sightings를 만들고 연결·개수·보존 필드를 검증한다. 이미 새 writer가 만든 더 최신 대상이면 원본 매핑과 revision을 검사한 후 skip한다. 임의 `ON CONFLICT DO UPDATE`로 현재 큐레이션 결과를 덮어쓰지 않는다.
6. checkpoint는 같은 transaction에 기록한다. 실패한 행의 checkpoint만 진행되는 상황을 금지한다.
7. 재실행은 source ID/버전/checksum으로 이미 완결된 작업인지 판정한다. UUID가 있다는 이유만으로 부분 자료를 성공 취급하지 않는다. 불일치하면 자동 보정 대신 중단하고 원인을 보고한다.

현재 단일 종 21건의 count는 해당 sighting에 옮길 수 있으나, 숫자를 입력했다는 사실만으로 정확도 분류를 만들어내지 않는다. 실행 직전 여러 종 자료가 생겼다면 원래 전체 species 문자열과 bird_count를 snapshot에 보존하고, 각 종 수량을 NULL로 둔다. 임의 배분이나 모든 종에 같은 수를 복제하지 않는다.

schema_migrations의 checksum은 확정된 SQL 파일 바이트를 기준으로 외부 runner가 계산한다. 적용된 version의 checksum이 다르면 실패한다. 스키마가 우연히 존재한다는 이유로 해당 migration을 과거에 실행했다고 기록하지 않는다. 미기록 기존 구조는 사전검사 결과로 확인하고, 실제 새 실행 시점만 기록한다.

## 9. shadow-read와 합격 기준

실제 응답은 기존 경로에서 제공하고 같은 요청 조건으로 신규 모델의 호환 어댑터 결과를 내부 비교한다. raw DB 행과 API JSON은 비교 목적을 분리한다. JSON 배열 순서와 NULL/누락의 차이는 계약에 맞춰 비교하고, generatedAt 같은 응답 생성 시각만 명시적으로 제외한다.

D1 Session은 순차 일관성을 제공하지만 별도 두 요청이 동일 시점 snapshot이라고 보장하지 않는다. 가능한 한 old/new SELECT를 한 read batch에 묶거나, 대상 revision/전역 변경 sequence를 앞뒤로 읽고 변경된 비교는 제외 후 재시도한다. 서로 다른 캐시·복제본의 결과 차이를 데이터 손실로 오인하지 않는다. [D1 Sessions와 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/)

| 경로 | 반드시 비교할 내용 |
|---|---|
| POST /reports | 수락 응답 형식·UUID·상태·대략 좌표 재사용·이름 비노출. 정책 확인 누락 거부는 별도 계약 변경 시험 |
| GET /reports/approved | spots/fixedSpots 구조, ID, 종 배열, history, 표시 좌표 선택, 연결 이력, 이름 공개 결과 |
| GET /reports/pending | pending AND pending_public, 정상 대략 좌표 쌍만 반환, 실제 위치·이름·메모 부재 |
| GET /reports/site/&lt;id&gt; | status/site_id 조건, observed_on→received_at→id 순서, limit/offset/total, 빈 마지막 페이지, 좌표 부재 |
| GET /reports/&lt;uuid&gt;/status | status/publicVisibility/receivedAt/decidedAt, 알 수 없는 ID의 기존 오류 |
| 관리자 목록·액션 | 승인·반려·공개취소·이름 동의·공개 대기·탐조지 연결·spot 연결/해제, 실패 원자성, 오래된 revision 충돌 |

전체 건수, 상태별 건수, site_id 분포, NULL/빈 문자열, 종 원문, count, 세 종류 좌표, 동의 원값, spot 연결을 함께 비교한다. 허용하는 의도적 차이는 항목별 운영 승인 기록이 있어야 한다. 미설명 누락·중복·좌표 노출·이름 노출 차이 0건이 읽기 전환 조건이다.

비교 로그는 값 자체를 저장하지 않는다. 요청 종류·불투명 ID·필드명·불일치 종류·집계·revision 정도만 기록하며, 종/좌표/이름/IP 해시/메모/원문 JSON을 남기지 않는다. 숫자 좌표를 반올림해 로그에 남기는 것도 금지한다.

## 10. rollback과 신규 API 출시

읽기 문제는 설정으로 `reports` 기반 호환 어댑터로 되돌린다. 되돌리는 대상은 **새 정책·삭제 차단·동의·guard를 아는 호환 코드**다. 확인 없이 저장하거나 삭제된 금지정보를 다시 공개하는 구버전 Worker로 되돌리지 않는다. 읽기 source를 되돌려도 `pair` 쓰기와 guard는 유지한다. `reports_only`는 승인된 초기 준비 상태이며 dual-write 개시 후 일반 rollback을 위한 모드가 아니다.

| 장애 | 복귀 조치 | 데이터 보존 조건 |
|---|---|---|
| 신규 읽기 어댑터 오류 | 읽기 source만 reports로 전환 | atomic dual-write 유지, 원인 분석 전 신규 테이블 삭제 없음 |
| 신규 쓰기/변환 오류 | 실패 요청 전체 롤백, 안전한 정책 인식 호환 writer 또는 일시 접수 차단 | 한쪽만 성공 응답 금지; 손상 가능성이 있으면 쓰기 계속하지 않음 |
| 배포 코드 문제 | 검증된 policy-aware 직전 버전으로 전환 | gate/epoch와 호환되는 버전인지 검사 |
| 금지자료 삭제 진행 중 | 공개 차단을 계속 유지 | rollback으로 purge tombstone·차단 목록을 무시하지 않음 |
| DB 전체 손상 | 승인된 재해복구 절차 | 최신 정상 접수와 삭제 tombstone 재적용, Time Travel은 최후 수단 |

복귀 중에도 새로 성공한 접수분이 양쪽에 있어야 한다. 상세 checklist 기능의 출시를 미루면 reports가 표현할 수 없는 자료의 손실을 피할 수 있다. 향후 상세 기능 출시 후에는 보고용 legacy 투영과 canonical 원자료를 구분하고, 기존 reports만으로 모든 최신 기능을 복구할 수 있다고 주장하지 않는다.

새 API는 별도 버전 경로에서 시작한다. 기존 GET의 응답 필드를 바로 바꾸지 않는다. 순서는 내부 신규 읽기 → shadow-read → 기존 형식의 신규 어댑터 → 정책 인식 관리자 쓰기 → legacy 복귀 기간 종료 → 상세 checklist/첨부 등 신규 기능이다. 실제 쓰기 dual-write 준비는 backfill 전에 완료되어야 하므로 ‘관리자 쓰기 전환’은 canonical 기준을 바꾸는 단계이며 초기 atomic 호환 writer 도입과 구분한다.

운영 전체 Time Travel restore는 DB를 제자리에서 덮어쓰고 진행 중 요청을 취소한다. 특정 행을 새 DB로 복제하는 기능처럼 계획하지 않는다. 별도 복구 시험 환경과 최신 접수 재생 계획이 필요하다. 이번 단계에서는 export·restore를 수행하지 않았다. [Cloudflare 복원 동작](https://developers.cloudflare.com/d1/reference/time-travel/)

## 12. 필수 시험과 운영자 결정

합성 자료만 사용하는 Phase 2 시험은 다음 실패 상황을 반드시 포함한다. 이번 Phase 1에서는 SQL이나 테스트 데이터 삽입을 실행하지 않는다.

- 확인 누락/false/잘못된 타입/구화면/직접 요청이 raw·reports·로그에 원문을 남기지 않는지.
- 기존 unknown 21건의 승인·반려·좌표·원문·동의·NULL이 그대로 보존되는지.
- 희귀종·보호종·계절만으로 자동 차단하거나 비공개하는 코드가 신규 경로에 남지 않는지.
- 한 batch의 각 문장 위치에서 오류를 주입해 양쪽 자료·review·audit·permit이 모두 롤백되는지.
- CAS 0행, 오래된 관리자 화면, 중복 요청·다른 본문의 같은 요청 ID, 응답 유실 재시도.
- backfill 중 승인·좌표 변경·site/spot 연결·이름 동의 변경·예외 삭제가 발생하는 경우.
- 구 Worker 단독 DML·직접 SQL·미닫힌 permit·잘못된 epoch가 guard를 통과하지 못하는지.
- raw 정상 수정/삭제가 차단되고 예외 purge만 관련 사본 전체를 제거하는지.
- 삭제 대상이 연결의 부모인 경우 실제 좌표가 새롭게 공개되지 않는지.
- 공개/대략 좌표 한쪽 NULL, 미등록 site, 고아/자기/순환 spot, 잘못된 동의값.
- 여러 종과 하나의 count, 미상 count, effort 누락, taxonomy split/merge 후 과거 원문 보존.
- 금지정보 발견→미디어 삭제 실패→재시도→복귀→복구 후 재삭제의 전 과정.
- 조회 sort/pagination/total/cache, 이름 동의 철회, 반려/공개취소의 old/new 응답 동등성.

Phase 2 전에 운영자가 직접 결정할 항목은 다음과 같다.

1. 필수 확인 계약의 발효 시각과 구화면 거부·새로고침 안내. 정확한 정책 버전 문자열과 지원 기간.
2. 종과 무관한 신규 pending 공개 방식. 기존 pending_public 원값은 보존하되 향후 접수의 승인 전 공개 기본값을 정한다.
3. 금지정보 확인·예외 삭제의 권한자, 잘못된 판정 이의 처리, 서비스 제거 기한, 백업 잔존 허용 기간. 삭제한 원문으로 재검토해야 하는 구조는 요구하지 않는다.
4. 원자료·제보자 표기·IP 해시·일반 반려·일반 audit/로그·외부 사본의 보존 기간과 접근권한. 금지자료에는 별도의 짧은 제거 기준을 적용한다.
5. 구 writer 차단을 위한 gate/permit/guard 구현, 일시 접수 중단 허용 범위, 전환·복귀 책임자.
6. legacy 복귀 지원 기간과 상세 checklist 기능 출시 시점. 손실 있는 reports 투영을 무손실 rollback으로 승인하지 않는다.
7. counts 정확도 입력 정책, 0의 허용 의미, protocol 어휘, complete_list 문구, taxa의 권위 출처·버전·검증 책임자.
8. 미디어 저장소·권리·삭제와 객체 버전 처리, 환경자료의 출처·관측/예보/모델 구분. 이번 단계에서 저장소를 생성하거나 과거 환경값을 채우지 않는다.

이 문서가 남기는 핵심 실행 제한은 두 가지다. 첫째, 확인 없는 기존 POST 수락과 필수 확인은 동시에 유지할 수 없으므로 계약 강화 시점을 명시한다. 둘째, D1의 일반 삭제와 복구 기록의 즉시 물리 제거는 다르므로 삭제 완료 범위를 사실대로 정의한다. 두 항목을 숨긴 채 무중단·완전 삭제를 보장하지 않는다.

## 13. v1.1 입력 계약과 capability 설계

서로 다른 버전을 혼용하지 않는다. 데이터 표준은 `1.1`, 입력 계약은 `reports-v1.1`, 수집 정책은 `non-breeding-v1`, raw payload 스키마는 `submission-v1.1`이다. DB 적용 버전은 별도 정수 1001 이후 순번이다. 정책 내용은 확정이며 문자열 이름·발효일은 배포 전 운영자가 확정한다.

향후 `GET /reports/capabilities`를 `Cache-Control: no-store`로 제공하는 안을 채택한다. 응답은 `{ok:true,inputContractVersion:"reports-v1.1",policyVersion:"non-breeding-v1",confirmationRequired:true,acceptingSubmissions:true}`이다. 스키마 번호·내부 epoch·관리자 정보는 공개 응답에 넣지 않는다. 실제 확인값은 POST JSON의 `contractVersion`, `policyVersion`, `nonBreedingConfirmed`, `requestId` 필드로 전달한다. 서버는 지원 버전과 정확한 boolean true를 검증한다. 커스텀 헤더 추가 없이 현재 Content-Type CORS 경계를 유지한다.

새 화면이 capability 404/실패/미지원 버전/접수 중지 상태를 받으면 제출 버튼을 비활성화하고 새로고침 또는 재시도를 안내한다. 이를 확인 면제로 해석하지 않는다. capability 캐시나 클라이언트가 속여도 최종 DB mutation의 epoch/permit 검사를 통과해야 한다. 관리자 인증 경로에서 양쪽 Worker의 writer protocol과 지원 schema/epoch 준비 여부를 확인한 후 gate를 전환한다.

| 상황 | HTTP / code | 사용자 메시지 / 재시도 |
|---|---|---|
| 확인 누락·false·타입 오류 | 400 NON_BREEDING_CONFIRMATION_REQUIRED | 번식 관련 관찰이 아님을 확인해 주세요. 자동 재시도하지 않음 |
| 입력/정책 버전 미지원 | 409 INPUT_CONTRACT_UNSUPPORTED / POLICY_VERSION_UNSUPPORTED | 화면을 새로고침한 뒤 다시 확인해 주세요. 재확인 후 제출 |
| 전환 중 쓰기 불가 | 503 WRITE_TEMPORARILY_UNAVAILABLE | 제보 접수를 준비 중입니다. 잠시 후 다시 시도해 주세요. 동일 requestId로 backoff, Retry-After 사용 |
| 관리자 오래된 revision | 409 REVISION_CONFLICT | 최신 상태를 확인한 후 다시 처리해 주세요. 묵시적 덮어쓰기 금지 |
| 같은 requestId에 다른 본문 | 409 IDEMPOTENCY_CONFLICT | 요청 식별자가 이미 사용되었습니다. 자동 재시도 금지 |
| 기존 중복 제보 | 기존 409 DUPLICATE_REPORT | 현재 중복 제보 계약 유지 |

오류 형식은 기존 `{ok:false,error:{code,message}}`를 유지하고 민감 본문을 echo하지 않는다. 현재 POST의 넓은 `UNIQUE|constraint` 예외 처리는 향후 guard/CHECK 실패까지 중복 제보로 오인할 수 있다. Phase 2에서는 고유성 위반, stale epoch, 정책 오류, 데이터 변환 실패를 구분해야 한다.

기존 13건은 `count_value=1,count_accuracy=unknown`, 8건은 `NULL,unknown`으로 보존한다. SQL CHECK는 unknown과 숫자의 공존을 허용한다. AI·규칙 기반 번식 가능성 추정에 의한 자동 차단이 0건인지 정책 시험에 추가한다.

비민감 purge tombstone의 DB 위치는 `audit_log`로 확정한다. `action='forbidden_content_purged'`, `target_type='report'`, `target_id=기존 UUID`를 사용하며 before_json과 after_json은 모두 NULL을 CHECK로 강제한다. 사유는 고정 action 코드로 표현하고 처리 단계는 민감 payload 없는 별도 감사 이벤트로 기록한다. 원문·좌표·종·이름·본문/파일 hash는 금지한다. 복구 대상 DB와 독립적인 동일 tombstone 보관 방법은 운영자 결정 항목이다.
