## 0. 결론 요약

1. **[확정] 지속 회색의 원인 경로는 두 RCA가 일치하고 이번 독립 재현도 같다.** 소수 실패 배치는 `partial_error`로 끝나고
   마감 타이머가 해제되며, 실패 칸은 Leaflet `_tiles`에 남아 다시 요청되지 않는다. 429·502·503 모두 화면 결과가 같다(6장 T1).
2. **[확정] 브라우저는 상태 코드를 구별할 수 없다.** 타일은 `<img>`로 받으므로 `tileerror`에는 HTTP 상태·`Retry-After`·
   `X-Tile-Upstream`이 없다. 따라서 "429면 대기, 502면 즉시" 같은 코드별 재시도는 **현 구조에서 구현할 수 없다.**
   클라이언트 재시도는 코드에 관계없이 **최악(429)에 맞춘 한 가지 정책**이어야 한다.
3. **권장 최소 수정안(R1)**: 프런트 1개 파일. 실패 칸만, **≥60초(+지터) 뒤**, **1칸 선발(카나리)이 성공할 때만 나머지 최대 7칸**,
   **칸(z/x/y)당 자동 1회**, **재시도 칸은 장애(OSM 전환) 판정에서 제외**, 안내는 현재 화면 결손 기준. 시제품(+67/−4줄)으로
   실제 Leaflet 1.9.3 + Chrome에서 회색 해소·요청 상한·토큰/타이머 보존을 확인했다(6장).
4. **반대(7장)**: 재시도 칸을 기존 장애 판정에 그대로 넣는 방식(시험에서 **위성 전체가 OSM으로 바뀌고 잠김**), 60초 미만 재시도,
   쿼리 문자열 캐시 무효화(Worker가 **404**로 거부: `worker.mjs:42`), 자동 `redraw()` 전체 재요청, 장애 기준을 1~2장으로 낮추기,
   회색 해결 명목의 리미터 상향·캐시 도입.
5. **Codex 수정안**: Codex RCA 8장은 대안 A~E를 **제안만** 했다. 이후 15:38에 설계 문서
   `VWorld-minimal-fix-design-2026-11-11.md`(M1)를 냈으나 이것도 **구현·시험 전 설계**다. 그래서 패치 대 패치 비교는 아직 할 수 없고,
   **설계 대 설계로 비교**했다. 두 설계가 갈리는 지점은 시제품으로 실측했다. 결과는 13장에 있다.

> **13장 비교 뒤 갱신된 권고(R1+)**

## 4. 429 재시도가 제한을 악화시키는지

**[확정] 시험(6장 T2, T3, T10)**
- 지속 429에서 권장안은 **재시도 주기마다 정확히 1건**(카나리)만 보내고, 실패 칸을 칸당 한 번씩 시도한 뒤 멈춘다.
- 순진한 재시도는 실패 칸 전부를 한꺼번에 다시 보낸다. 그 4장이 또 실패하자 기존 장애 판정에 걸려 **OSM 전환·잠금**이 됐고,
  60초 뒤 복구 시도가 **한 화면 전체(24장)**를 다시 요청하게 된다. 즉 순진한 재시도가 오히려 요청을 늘린다.

**[가설] 요청량 영향(명목값 180/300 기준)**

| 상황 | 이용자 1명이 추가로 보내는 Worker 요청 | 비고 |
|---|---|---|
| 일시 실패 k칸(k≤8) | k건(1회) | 지금은 사용자가 OSM↔위성을 눌러 화면 전체(24~48건)를 다시 받는 것이 유일한 복구 |
| 일시 실패 k칸(k>8) | 8건, 나머지는 다음 `load` 뒤 다음 라운드(칸당 1회) | |
| 지속 429(창이 계속 꽉 참) | 60초당 1건, 칸당 1회까지 | 기존 전체 장애 복구는 60초에 한 화면(24~48건) |
| 탭 숨김 | 0건(보일 때까지 미룸) | |

- **다수 이용자**: CGNAT·학교망처럼 한 IP를 여럿이 쓰면 재시도도 그 IP 예산을 쓴다. 상한(이용자당 60초 1건 + 성공 시 ≤7건)이 작아
  공유 예산 잠식은 작다 **[가설]**. 전역 리미터가 포화되면 모든 이용자가 같은 시각에 60초 타이머를 걸 수 있어 **동시 재시도 파동**이
  생길 수 있다 → **0~15초 균등 지터** 권장(기존 60/120/240/480 복구에도 지터가 없다는 점은 별도 과제).
- **Cloudflare 일일 한도(Free 10만)**: 429·502를 포함한 모든 재시도가 1건씩 소모한다. 위 상한 안에서 일상 영향은 작으나,
  실제 하루 사용량이 **[미확인]**이라 배포 전 기준선이 필요하다.
- 리미터가 거절한 호출도 카운터에 더해지는지 **[미확인]**. 더해진다면 60초 미만 재시도는 차단 시간을 늘린다 → 60초 미만 금지 근거.

## 7. 반대할 수정안

1. **재시도 칸을 기존 장애 판정(`outage`)에 그대로 세는 방식** — T2·T3에서 위성 4칸 재실패만으로 `tile_error`·잠금·OSM 전환.
   이후 60초 복구가 한 화면 전체를 다시 요청한다. 무자료 칸이 영구 실패라면 회색 → OSM → 복구 → 회색 → OSM이 60/120/240/480초로 반복된다.
2. **60초 미만 자동 재시도, 횟수·칸 상한 없는 재시도, 지수 백오프 없는 반복** — IP 창 안에서는 429만 늘고, 거절 호출이 카운터에
   더해진다면 차단을 연장한다 **[미확인 전제]**.
3. **쿼리 문자열·해시를 붙인 캐시 무효화** — `tileAt()`이 404를 돌려준다(F11).
4. **부분 실패 때 자동 `redraw()`·레이어 재생성** — 매번 한 화면(24~48장, 하이브리드 위성 포함) 재요청.
5. **장애 기준을 1~2장으로 낮추기(Codex D)** — 일시 오류 한 장으로 위성 전체를 잃고, 복구 요청이 늘어난다.
6. **회색 해결을 명목으로 한 리미터 상향·브라우저 캐시 도입** — 병목이 일일 10만·VWorld 키 한도로 옮겨 가고, 캐시는 VWorld 사전 승낙이 필요(약관 19조, Claude RCA 3.8).
7. **세대 토큰·배치 번호·`later()`·타이머 정리 경로를 우회하는 구현** — 예: 재시도 타이머를 `detachVworld`·`destroy`에서 지우지 않거나,
   Leaflet `load` 이벤트 안에서 바로 `_update()`를 부르는 구현(10/28 `_fadeAnimated` 예외와 같은 계열 위험).

## 8. 권장 최소 수정안(R1) 명세

변경 파일: `assets/birdmap-basemap.js` 하나(Worker·Lambda·`index.html` 변경 없음). 시제품 diff는 `…-recovery-design-review/proto.diff`.

1. 상수: `PARTIAL_RETRY_MS = 60000`(+0~15 s 지터), `PARTIAL_RETRY_MAX = 8`. 시제품은 시험을 위해 `window.__birdmapPartialRetryMs`로
   줄였다. **제품에는 넣지 않는다.** 지터는 시제품에 없다(설계 권고만, 시험 안 함).
2. `_viewTiles()`가 현재 화면의 실패 칸 키 목록(`failed`)도 돌려준다.
3. `_retryTiles(keys)`: 해당 칸을 `_removeTile`로 지우고 Leaflet `_update()`가 같은 URL로 다시 만들게 한다(쿼리 문자열 없음, `no-store`라 실제 재요청).
4. 주 레이어 `load`에서, 표시된 레이어(`drawn`)의 화면에 **아직 자동 재시도하지 않은** 실패 칸이 있으면 재시도 타이머 1개를 예약한다.
5. 타이머 발화 시 다음이면 아무것도 안 한다: `current(token, layer)` 거짓, 카나리 진행 중, 배치 진행 중(`layer._loading`),
   줌 휴식·애니메이션 중, 탭 숨김(이때는 다시 예약). 다음 `load`가 다시 예약한다.
6. 카나리 1칸을 먼저 재요청한다. 그 배치의 `load`에서 카나리 결과를 본다.
   - 성공: 나머지(최대 7칸)를 그 자리에서 "시도함"으로 표시하고, **다음 턴(`later`)**에 재요청한다.
   - 실패: 그 라운드를 끝낸다. 남은 칸이 있으면 다음 라운드가 다시 카나리 1칸으로 시작한다.
   - 따라서 지속 실패에서는 주기당 1건씩, 칸당 한 번 뒤 멈춘다(T2).
   - 더 보수적인 변형: 카나리가 실패하면 그 레이어의 자동 라운드를 끝내고 R2(수동)만 남긴다.
7. 재시도 칸의 `tileload`/`tileerror`는 `batchSuccesses`/`batchErrors`에 **넣지 않는다**(마감 재무장만). 장애 판정은 새 칸만으로 한다.
8. 안내: `reason = batchErrors > 0 || 화면 실패 칸 있음 ? 'partial_error' : …` — 다른 칸이 성공해도 회색이 남아 있으면 안내 유지.
9. 정리: `detachVworld()`·`destroy()`에서 재시도 타이머·재시도 집합 해제(세대 토큰 검사와 이중 보호).
10. 하이브리드 지명 레이어: 이번에는 적용하지 않는다(지명 누락은 회색이 아니고 요청이 2배가 된다). 필요하면 같은 방식으로 별도 변경.

**[확정] 보존한 것**: 세대 토큰·레이어 동일성(`current`), 배치 번호(`failLater`), `later()` 지연, 12 s 마감 의미, 장애 기준식,
60/120/240/480 s 복구와 90% 복귀 기준, 정착 타이머·idle 검사 정리, 하이브리드 지명 레이어 독립 판정. 기존 메모리 시험 34건 통과
(시제품은 메모리 스텁의 `_viewTiles`에 `failed: []`만 보충해야 함 — 실제 변경 시 시험 하네스도 함께 고쳐야 한다).

### 13.2 갈리는 지점 실측: 재실패 뒤 OSM 대체 여부

조건: 1366×768, 위성 24장 중 4장. 모든 대기는 1/20로 줄였다(재시도 60 s→3 s, 복구 60/120/240/480 s→3/6/12/24 s).
괄호 안 시간은 실제 시간으로 환산한 값이다.

**T12a: 4칸이 영구 실패(502)**

R1+(proto2)는 회귀 시나리오 전체(T1~T11 대응 17개)도 통과했다.
- 일시 실패: 추가 요청 2건으로 회색 해소
- 지속 429: 60 s당 1건
- OSM 선택·줌·destroy 취소: 대기 중 재시도 0건
- 하이브리드·모바일 390×844: 정상
- 전부 429와 무응답: 기존 경로 그대로
- 페이지 예외 0건, 같은 URL 200 ms 안 중복 0건

**병합안을 처음 시험할 때 잡은 결함**
- 칸별 백오프를 넣자 대기가 끝난 칸이 여럿일 때 카나리 라운드가 0초 간격으로 이어졌다(지속 429에서 3 ms 안에 3건).
- 레이어당 라운드 간격을 최소 60 s로 강제해 고쳤다(`lastRound`). 고친 뒤 재시험에서 60 s당 1건을 확인했다.
- 실제 구현에서도 이 시험을 회귀 항목으로 넣어야 한다.

### 13.3 판단

- **동의(채택)**: 상태 코드 판단, 60 s 이상 대기와 지터, 실패 칸만 재요청, 화면 결손 기준 안내, M2·M4에 대한 판단, M1의 공유 예산·동시 2·750 ms·숨김 탭 처리, M1 7장 검증 계획.
- **수정 권고**: M1 "칸당 1회" → 칸당 최대 4회 백오프(T12b). M1에 카나리 추가(지속 429에서 요청 8배 차이 **[가설]**).
- **반대 권고**: M1 4.4 "재실패 → `fail()` OSM 대체". 영구 실패 칸이 하나라도 있는 화면에서는 위성이 OSM으로 잠기고 요청이 늘어난다(T12a).
  다만 영구 실패 칸이 실제로 있는지(VWorld 무자료 칸의 응답 형태)는 **[미확인]**이다. 없다면 이 차이는 "일시 장애 때 회색으로 기다리느냐, OSM으로 잠시 바꾸느냐"로 줄어든다.
- **사용자 결정 필요**: 재시도까지 실패한 칸이 남을 때 **위성 유지+회색 칸**(R1+)과 **OSM 전환**(M1) 중 어느 쪽을 택할지.
- **사용자 결정(2026-11-11): 위성 유지(R1+).**
  - 재시도까지 실패한 칸이 남아도 OSM으로 바꾸지 않는다. 회색 칸과 안내를 유지한다.
  - 칸별 백오프(60/120/240/480 s)를 다 쓰면 자동 재시도를 멈춘다.
  - 이후 구현은 R1+에 M1의 공유 예산(60 s당 8건)·동시 2건·이동 후 750 ms·숨김 탭 취소를 더한 형태를 기준으로 한다.
  - 구현·커밋·PR·배포는 아직 승인되지 않았다.
