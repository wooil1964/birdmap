## 0. 요약

1. **회색 칸은 "실패 비율"로 결정된다. 어느 구간이 실패했는지와는 관계없다.**
   - 한 묶음(Leaflet이 한 번에 요청한 타일들)에서 실패가 적으면 VWorld를 유지한다(`partial_error`). 적다는 것은 실패가 3장 미만이거나, 성공과 대기 중인 타일을 합친 수 이하라는 뜻이다(`assets/birdmap-basemap.js:304-306`).
   - 실패 타일은 Leaflet 1.9.3에서 숨김 처리되고, 그 자리의 상위 레벨 타일도 정리된다. 그래서 지도 바탕색 `#ddd`(회색)가 그대로 보인다.
   - 줌 6 이상이고 화면 전체가 국내 범위 안이면 OSM 배경도 이미 제거돼 있다(`:141-146`).
   - 실패가 많거나 12초 동안 아무 응답이 없을 때만 OSM으로 전환한다.
2. **회색 칸은 자동으로 다시 요청되지 않는다.**
   - 60·120·240·480초 자동 복구는 OSM 전환(잠금) 때만 동작한다(`:284-294`, `:323-330`).
   - 회색 칸이 다시 요청되는 경우는 다음뿐이다: 줌 레벨 변경, 2칸 밖까지 이동했다가 돌아오기, 지도 종류 변경, 새로고침.
   - 같은 종류를 다시 눌러도 다시 요청하지 않는다(시험으로 확인).
3. **가장 개연성 높은 원인은 Worker 요청량 제한 429다(추정, 운영 미확인).**
   - 하이브리드는 위성과 지명 레이어를 함께 요청하므로 화면당 요청이 2배다. 1920×1080이면 약 96~108건이다.
   - 따라서 IP당 180/60초 한도에 1분에 2화면 남짓이면 닿는다.
   - 10/28 Codex 모의 시험에서 1920×1080 마지막 화면 54장 중 12장이 429를 받았고, 결과는 `partial_error`였다. 즉 VWorld가 유지된 채 12칸이 비었다(`docs/reviews/basemap-pc-wheel-settle/2026-10-28-codex-round3.md:83,88`).
4. **코드상 같은 회색을 만들 수 있는 다른 원인**(모두 운영 미확인):
   - VWorld 응답 6초 초과
   - VWorld의 HTTP 오류, XML 예외, 형식 불일치, 이미지 검증 실패
   - Lambda 동시 실행 스로틀
   - 콜드 스타트와 지연이 겹쳐 Worker 8초 제한 초과
   - Workers Free 요청당 CPU 10ms 초과(오류 1102)
   - 바다나 고배율 같은 무자료 칸을 VWorld가 오류로 응답할 가능성. 그렇다면 그 칸은 원인과 상관없이 늘 회색이다. 실제 응답 형태는 미확인이다.
5. **10/28 보고서 이후 바뀐 코드**
   - Worker(`vworld-tiles/src/worker.mjs`)와 Lambda(`vworld-relay/index.mjs`): 10/28 기준 커밋 `3a24a4a` 이후 변경 없음(`git diff` 결과 없음).

6. **원인을 확정하는 방법**: 회색이 보일 때 아래 둘이면 구간을 거의 가를 수 있다(7장).

## 3. 변경 내용(조사 결과)

코드 변경은 없다. 아래는 조사 결과다.

### 3.1 경로와 화면 표시 규칙

```
브라우저(Leaflet <img>)
  → Worker birdmap-vworld-tiles (Cloudflare 별도 계정, 지정 배치)
      Origin/Referer 확인 · 범위 확인 · IP/전역 리미터 · SigV4 서명 · 8초 제한 · 이미지 재검증
  → 서울 Lambda 함수 URL (AWS_IAM, Node 22, arm64, 128MB, 함수 제한 10초)
      호출자 확인 · 범위 확인 · 6초 제한 · 이미지 검증
  → api.vworld.kr WMTS (Base PNG / Satellite JPEG / Hybrid 투명 PNG)
```

**타일 한 장**
- 200과 올바른 이미지면 표시한다.
- 그 밖의 모든 응답은 Leaflet `tileerror`가 된다. 상태 코드가 무엇이든 페이지는 알 수 없다.
  - Chrome은 오류 응답(`text/plain` + `nosniff`)을 ORB로 차단한다. 그래서 콘솔에는 `ERR_BLOCKED_BY_ORB`만 보인다(`docs/reviews/basemap-pc-wheel-settle/claude-report.md:34`).

**레이어 판정**(`assets/birdmap-basemap.js:304-306`)
- 다음 중 하나면 장애로 판정한다.
  - 실패가 3장 이상이고, 성공과 아직 응답 없는 타일을 합친 수보다 많다.
  - 아직 아무것도 표시하지 못한 레이어가 실패만 받았다.
- 장애 판정이면 OSM으로 전환한다(`:323-330`). 판정 처리는 다음 턴에 실행한다(`:312-314`).
- 장애가 아니면 VWorld를 유지하고 `partial_error`로 표시한다(`:611`).
  - 안내 문구: "일부 지도를 불러오지 못했어요 · OSM을 선택할 수 있어요"(`:193`)

**12초 마감**(`:10`, `:342-350`)
- 묶음에 12초 동안 아무 활동이 없으면 `tile_timeout`으로 OSM 전환한다.

**OSM 배경 유지 조건**(`syncBackdrop`, `:141-146`)
- 다음 경우에는 OSM 배경을 남긴다.
  - 줌 6 미만
  - 화면이 국내 범위(`KOREA_VIEW_BOUNDS`, `index.html:3898`)를 벗어남
  - OSM에서 VWorld로 돌아오는 중이고, 첫 성공 묶음 전
- 그 밖에는 성공 타일이 1장 이상인 묶음이 끝나면 OSM을 제거한다.

**Leaflet 1.9.3 동작**(jsDelivr 공개 소스 `GridLayer.js`·`leaflet.css` 확인)
- 오류 타일도 `loaded`와 `active`가 된다. 그래서 상위 레벨 타일을 남겨 두지 않고 정리한다(`_tileReady`, `_updateOpacity`, `_pruneTiles`).
- 오류 타일에는 `leaflet-tile-loaded` 클래스가 붙지 않는다. `.leaflet-tile { visibility: hidden }` 규칙 때문에 보이지 않는다.
- 결국 `.leaflet-container { background: #ddd }`가 보인다.
- `index.html:30-37`은 이 배경을 바꾸지 않는다.

| 상황 | 화면 |
|---|---|
| 묶음 실패가 적음 + 줌 6 이상 + 화면 전체가 국내 범위 안 | **회색 칸(#ddd)**. "일부 지도를 불러오지 못했어요" 안내 |

| V-4 | VWorld | 다른 Content-Type(점검 HTML, `image/jpg` 같은 변형 등. 실제는 미확인) | `relay-not-jpeg-type`, `relay-not-png-type` | 적으면 회색, 많으면 OSM | `worker.mjs:180-184` |
| V-5 | VWorld | 이미지 검증 실패. JPEG: 128바이트 미만, 스캔 전에 256×256 프레임 없음, EOI가 맨 끝이 아님(뒤에 여분 바이트). PNG: 256×256이 아님, CRC 불일치, IEND 뒤 여분 | `relay-jpeg`, `relay-png` | 적으면 **회색**, 많으면 OSM | `worker.mjs:65-107` |
| V-6 | VWorld | 2MB 초과, 본문 스트림 오류 | `relay-body` | 적으면 회색, 많으면 OSM | `worker.mjs:109-131` |
| V-7 | VWorld | 연결 실패(AWS 출구 차단, DNS, TLS) | `relay-network` | 전면이면 OSM | `worker.mjs:167`, `:195` |
| V-8 | VWorld | 키별 호출량·전송량 한도 초과(약관 13조, 수치 미확인) | V-2나 V-3 형태로 예상(미확인) | 전 사용자 전면 실패, OSM 전환 | 10/28 정책 조사 3.7 |

**정리**
- 회색이 되는 것은 **일부 타일만** 실패하는 유형이다: W-6, W-7, W-10, L-4, L-5, V-1, V-2, V-5, C-2.
- 설정·인증·키 문제는 모든 타일을 실패시키므로 회색이 아니라 **OSM 전환**으로 보인다: W-3, W-4, W-8, W-9, L-1, L-2, L-3, V-8, C-1.

### 3.3 요청량 제한 구현

**위치와 순서**
- `vworld-tiles/src/worker.mjs:229-234`에 있다.
- IP 리미터(`CLIENT_TILE_LIMITER`)를 먼저 검사하고, 전역 리미터(`GLOBAL_TILE_LIMITER`)를 다음에 검사한다.
- IP에서 거절되면 전역 리미터의 `limit()`는 호출하지 않는다. IP를 통과한 뒤 전역에서 거절되면 IP 카운터는 이미 올라간 상태다.

**키**
- IP 리미터: `CF-Connecting-IP` 값 그대로 쓴다. IPv4 주소, 또는 IPv6 주소 하나(/128)다.
- 전역 리미터: 고정 키 `birdmap-vworld-base`. 이름과 달리 Base·Satellite·Hybrid가 모두 이 키를 함께 쓴다.

**429 조건**
- `limit()` 결과의 `success`가 `true`가 아니면 429를 돌려준다.
- 두 리미터의 응답이 똑같아서(`429 tile_rate_limited`) 어느 쪽이 거절했는지 구분할 수 없다.
- `Retry-After` 헤더는 없다.
- binding 자체에서 예외가 나면 503으로 막는다(fail closed).

**창 계산**
- period는 60초다.
- Cloudflare 문서상 리미터는 근사적이고, 위치별로 따로 세며, 다른 인스턴스와 나중에 동기화된다. 그래서 설정값보다 많이 통과할 수 있다.
- 창이 고정인지 이동인지는 문서에 없다(**미확인**).
- 10/27 실측에서는 60초 창의 약 680건째에 첫 429가 나왔다(1회 측정, 2회 재현).

**설정값의 출처**
- 저장소에는 `wrangler.toml`이 없어 코드만으로 값을 알 수 없다.
- 180/300은 10/25 배포 도구 점검 기록에 있는 값이다. 현재 값은 **미확인**이다.

**거절과 하위 구간**
- 429는 Lambda와 VWorld를 호출하지 않는다.
- 그러나 Cloudflare 일일 요청 수에는 포함된다(3.8).

**IP 키의 한계**
- Cloudflare 문서는 IP를 키로 쓰지 말라고 권한다. 여러 사용자가 같은 IP를 공유하면 의도보다 넓게 제한되기 때문이다.
- 이동통신 CGNAT, 학교·회사망에서는 여러 사용자가 180/60초를 함께 쓸 수 있다(추정).
- 반대로 IPv6는 주소마다 따로 센다. 한 사용자가 주소를 바꾸면 IP 제한을 우회할 수 있고, 이때 최종 상한은 전역 리미터다.

**화면당 요청 수**
- 1366×768은 약 24장, 1920×1080은 약 48~54장이다(10/28 round3:60, codex-round3:88). 하이브리드는 2배다.
- 명목값 180/60초 기준으로 1분에 선명하게 볼 수 있는 화면 수:

  | 지도 | 1366×768 | 1920×1080 |
  |---|---|---|
  | 일반·위성 | 약 7.5화면 | 약 3.5화면 |
  | 하이브리드 | 약 3.7화면 | 약 1.7~1.9화면 |

- 전역 300/60초가 한 위치에 모인다면(10/28 추정), 1920×1080 하이브리드 기준 모든 사용자를 합쳐 1분에 약 3화면이다.
- Worker 응답이 `no-store`라 같은 타일을 다시 볼 때도 매번 요청한다. 10/27에는 요청 702건 중 고유 타일이 215장이었다.

### 3.4 하이브리드(위성 + 문자 레이어)

**구성**
- 주 레이어는 Satellite JPEG(zIndex 2), 겹침 레이어는 Hybrid 투명 PNG(zIndex 3)다.
- 두 레이어는 판정, 잠금, 복구, 12초 마감을 각각 따로 한다(`assets/birdmap-basemap.js:44-49`, `:486-545`, `:547-629`).

**실패별 화면**
- 위성 타일이 일부 실패: 회색 칸 위에 도로와 지명만 그려진다. 지명 레이어는 성공했을 때다.
  - **회색 칸에 글자만 있으면 위성 타일 실패의 특징이다.**
- 지명 타일이 일부 실패: 그 칸에서 지명만 빠지고 위성은 보인다.
- 지명 레이어가 장애 판정을 받거나 12초 무응답: 지명 레이어를 제거한다.
  - 안내: "도로·지명 표시를 불러오지 못해 위성영상만 보여요"(`:194`)
  - 지명 레이어만 60초부터 복구를 시도한다(`:332-340`).
- 위성 레이어가 장애 판정: OSM으로 전환한다. 지명 레이어도 함께 제거된다(`:256-271`).

**요청량**
- 요청이 2배라 리미터에 2배 빨리 닿는다.
- 위성과 지명 요청이 섞여 도착하므로, 429가 어느 레이어에 걸릴지는 도착 순서에 달려 있다.

**Worker와 Lambda의 처리**
- 같은 경로 규칙과 같은 리미터 키를 쓴다. 형식 검사만 레이어별로 다르다(위성은 JPEG, 하이브리드는 PNG).
- 검증 비용이 다르다.
  - PNG는 모든 청크의 CRC32를 비트 단위 JavaScript로 계산한다(`worker.mjs:56-63`, `:73`). Worker와 Lambda(128MB, 배정 CPU가 작음) 양쪽에서 수행한다.
  - 위성 JPEG는 스캔 시작 전 마커만 훑으므로 가볍다.
  - 따라서 증상이 주로 **위성 칸**이라면 CPU 초과(C-2)보다 429, VWorld 지연, 무자료 응답의 가능성이 더 높다(추정).

### 3.5 실패 뒤 정상 복귀 조건

**회색 칸(`partial_error`)**
- 자동 재요청이 없다. 복구 타이머도 예약되지 않는다(시험으로 확인).
- Leaflet은 오류 타일을 다시 요청하지 않는다. 회색 칸은 아래 경우에만 다시 요청된다.
  - 줌 레벨이 바뀌어 그 레벨의 타일이 정리됐다가 다시 만들어질 때
  - `keepBuffer`(기본 2칸) 밖까지 이동해 타일이 지워진 뒤 돌아올 때
  - 다른 지도 종류를 골랐다가 돌아올 때. 새 레이어가 화면 전체를 다시 요청한다.
  - 페이지를 새로고침할 때
- 같은 종류를 다시 누르면 기존 레이어를 그대로 쓴다(`:550-556`). 위성 ↔ 하이브리드 전환도 위성 레이어를 유지하므로 위성의 회색 칸은 그대로다.
- `partial_error` 안내는 다음 묶음이 오류 없이 끝나면 사라진다(`:611`). 회색 칸은 남을 수 있다.

**OSM 전환(`tile_error`, `tile_timeout`)**
- 지도 종류별로 메모리에 잠근다(`failedKeys`).
- 60·120·240·480초 뒤 자동 시도를 한 번씩 한다(`:20`, `:284-294`). 한 번의 시도는 한 화면 분량을 요청한다.
- 첫 성공 묶음 전까지 OSM을 아래에 유지한다.
- 시도한 묶음이 끝까지 진행돼 현재 화면의 90% 이상을 채우면 복귀로 보고 대기 단계를 초기화한다(`:25`, `:317-321`).
- 4번 모두 실패하면 OSM에 머문다. 이후에는 "다시 시도" 버튼으로만 풀린다(`:643-664`).
  - 이동, 확대·축소, 같은 종류 재선택으로는 풀리지 않는다.

**하이브리드 지명 레이어**
- 위와 같은 방식이지만 잠금과 복구를 따로 한다.

### 3.7 수집 가능한 지표와 오류 구분 방법

#### A. 사용자 브라우저

회색이 보인 그 순간에, 이미 일어난 요청만으로 확인한다. 추가 요청은 하지 않는다.

**화면 안내 문구**
- "일부 지도를 불러오지 못했어요" → 회색 경로(`partial_error`)
- "지도를 불러오지 못해 OSM으로 전환했어요" → 전면 실패
- "지도 응답이 늦어 OSM으로 전환했어요" → 12초 마감
- "도로·지명 표시를 불러오지 못해 위성영상만 보여요" → 지명 레이어 장애

**콘솔 `birdmapBasemap.getState()`**
- `index.html:6037`의 최상위 `var`라서 전역 변수다. 읽기만 한다.
- 확인할 값: `reason`, `errors`(현재 묶음의 실패 수), `overlayErrors`, `overlay`, `backdrop`, `locked`, `recoveryAttempts`
- 비밀값이나 요청 URL은 들어 있지 않다. 기존 시험이 이를 검증한다.

**개발자 도구 네트워크 탭과 HAR**
- `birdmap-vworld-tiles` 도메인으로 거른다.
- Chrome ORB 때문에 실패 요청이 차단으로만 보일 수 있다. 원래 상태와 헤더는 응답 헤더 탭, HAR, CDP로 확인한다. 브라우저 버전별 표시 방식은 **미확인**이다.

**응답 형태별 구분**

| 응답 | 의미 |
|---|---|
| 200 `image/jpeg`·`image/png` | 성공 |
| 429 `text/plain` `tile_rate_limited`, `X-Tile-Upstream` 없음, 약 0.1초 | Worker 리미터. IP인지 전역인지는 구분 불가 |
| Cloudflare HTML 오류 1027 | Workers Free 일일 한도 |
| Cloudflare HTML 오류 1102 / 1101 | CPU·메모리 초과 / 처리되지 않은 예외 |
| 503 `tiles_unavailable`, 분류 헤더 없음 | 비활성화, 비밀값, binding, 서명 예외 중 하나. 서로 구분 불가 |
| 502 + `timeout`(약 8초) | Worker → Lambda 8초 초과 |
| 502 + `http-403` | 함수 URL 인증 거절 또는 호출자 불일치 |
| 502 + `http-429` | Lambda 스로틀(추정) |
| 502 + `http-5xx` | Lambda 함수 오류 |
| 502 + `network` | Worker → Lambda 연결 실패 |
| 502 + `relay-timeout`(약 6초 이상) | VWorld 6초 초과 |
| 502 + `relay-http-NNN` | VWorld HTTP 오류. NNN은 VWorld 상태 코드 |
| 502 + `relay-xml-exception` | VWorld XML 예외(키, 한도, 파라미터) |
| 502 + `relay-not-jpeg-type` / `relay-not-png-type` | VWorld가 다른 Content-Type으로 응답 |
| 502 + `relay-jpeg` / `relay-png` | VWorld 이미지 검증 실패 |
| 502 + `relay-body` | 2MB 초과 또는 본문 오류 |
| 502 + `relay-network` | Lambda → VWorld 연결 실패 |
| 403 `source_not_allowed` | Origin/Referer 문제 |
| `cf-ray` 끝 세 글자 | 요청이 들어온 콜로(HKG, ICN 등) |

#### B. Cloudflare

VWorld 전용 계정에서 읽기 전용 단기 토큰으로 확인한다.

**지표**
- GraphQL `workersInvocationsAdaptive`를 스크립트별·시간별로 본다: `requests`, `subrequests`, `errors`, CPU 시간 분위수, `status`.
- `status`는 호출 상태다(성공, 예외, 자원 초과 등). HTTP 상태가 아니다.

**해석**
- `requests − subrequests`는 Lambda 앞에서 거절된 요청 수에 가깝다. 대부분 429로 추정하지만 403·404·503도 섞인다.
- 시간대별 분포를 보면 거절이 몰리는 시점을 알 수 있다.
- 하루 합계(UTC 기준)를 10만과 비교한다.
- CPU P99가 10ms 근처이거나 자원 초과 상태가 있으면 C-2를 의심한다.
- Worker가 직접 돌려주는 502는 스크립트가 정상 종료한 것이라 `errors`에 잡히지 않는다(코드상 판단). 그래서 502 분류는 Cloudflare 기본 지표로는 보이지 않는다.

**Workers Logs**
- HTTP 상태별 집계를 볼 수 있지만, 켜는 것 자체가 설정 변경이라 **승인이 필요하다**.
- Free 요금제는 하루 20만 이벤트, 3일 보관이다.
- 접속 IP 같은 개인정보가 수집될 수 있어 범위 검토가 먼저 필요하다.

#### C. AWS CloudWatch

서울 리전에서 읽기 전용으로 확인한다.

**지표**
- 함수 URL: `UrlRequestCount`, `Url4xxCount`, `Url5xxCount`, `UrlRequestLatency`(AWS 문서)
- Lambda: `Invocations`, `Errors`, `Throttles`, `Duration`, `ConcurrentExecutions`

**해석**
- VWorld가 실패해도 함수는 정상적으로 502를 반환한다. 그래서 `Errors`가 아니라 `Url5xxCount`에 잡힌다.
- `Url5xxCount ÷ UrlRequestCount`는 상위 구간(VWorld·함수)의 실패율이다.
- `Duration` 최댓값이 6,000ms 근처에 몰리면 VWorld 시간 초과(V-1)다.
- `Throttles`가 0보다 크면 L-4다.
- Cloudflare `subrequests`와 `UrlRequestCount`는 비슷해야 한다. 차이가 있으면 인증 실패 같은 문제다.

**주의**
- 함수 설정 조회 명령은 환경변수(VWorld 키)를 그대로 출력한다. 출력 필드를 반드시 제한한다(10/28 7장과 같음).
- 함수 실행 역할에는 로그 권한이 없어 CloudWatch Logs는 없다. 의도된 설계다.

#### D. VWorld

- 로그인 후 인증키별 사용량과 제한량을 볼 수 있는지 확인한다. 볼 수 있는지 자체가 미확인이다.

#### E. 판정 순서(제안)

1. 회색이 보일 때 HAR 1건과 `getState()` 결과를 받는다. 실패 타일의 상태와 분류 헤더로 W/L/V 중 어느 구간인지 가린다.
2. 429가 많으면 Cloudflare `requests − subrequests`의 시간대 분포와 하이브리드 사용 여부를 본다.
3. `relay-*`가 많으면 CloudWatch `Url5xxCount`와 `Duration`을 본다.
4. 바다, 경계, 고배율처럼 특정 칸만 반복해서 회색이면 VWorld 무자료 응답일 수 있다. 이때는 **승인을 받은 뒤** 해당 칸 1~2장만 확인한다.

### 3.8 요청량 제한과 요금제의 관계

**Cloudflare Workers Free**(공식 문서, 2026-11-11 열람)
- 하루 10만 요청. UTC 자정, 즉 한국시간 09시에 초기화된다.
- 요청당 CPU 10ms, 하위 요청 50개.
- 일일 한도를 넘으면 오류 1027, CPU·메모리를 넘으면 오류 1102다.
- 계산 대상은 Worker에 도달한 모든 요청이다. 429와 403도 포함된다.
  - 따라서 **리미터는 일일 한도를 보호하지 못한다.**
  - 전역 300/분은 이론상 하루 43만 2천 건으로, 10만보다 크다.
- 하루 10만 요청을 화면 수로 바꾸면(1920×1080 기준): 일반·위성 약 2,000화면, 하이브리드 약 1,000화면이다.
- 실제 하루 사용량은 **미확인**이다.

**Cloudflare Workers Paid**
- 월 $5. 1,000만 요청과 CPU 3,000만 ms가 포함된다.
- 초과분은 요청 100만 건당 $0.30, CPU 100만 ms당 $0.02다.
- 요청당 CPU 기본 한도는 30초이고, 일일 한도는 없다.
- 자동 비용 상한이 없으므로 리미터가 비용 상한 역할을 맡게 된다.

**리미터 binding**
- 추가 요금과 Free 요금제 제공 여부는 문서에서 확인하지 못했다.
- 10/25 기록상 현재 계정에서 동작했다.

**AWS Lambda**
- 비용은 요청 수, 실행 시간(GB-초), 인터넷 전송량으로 정해진다.
- 일반 상시 무료 한도는 월 100만 요청, 40만 GB-초다.
- 이 계정의 요금제 유형은 **미확인**이다. 2025-07 이후 신규 계정의 크레딧형 무료 플랜이라면 기간이 끝나거나 크레딧이 소진될 때 계정이 제한될 수 있으므로 확인이 필요하다.
- 비용 상한 추정(가정: Cloudflare Free 상한까지 모두 통과, 평균 0.3초, 128MB, 타일 평균 30KB):
  - 월 하위 요청 약 300만 건 → 요청 비용 약 $0.4
  - 실행 시간 약 11만 GB-초 → 무료 한도 안
  - 전송량 약 90GB
  - 10/25 기록의 추정은 월 $1.8~8이었다.
- 기존 경보: 하루 `Invocations` 5만(주의), 8만(긴급)(`vworld-relay/README.md`).

**VWorld**
- 인증키별로 호출 횟수와 전송량 제한이 있다. 수치는 **미확인**이다.
- 한도를 넘으면 그 키를 쓰는 서비스 전체가 중단될 수 있다(약관 13조).
- 사전 승낙 없이는 데이터를 저장할 수 없다(약관 19조). 그래서 지금은 캐시를 쓸 수 없다.

**병목 순서**(명목값 기준)
1. IP 180/분
2. 전역 300/분(위치에 모일 경우)
3. Cloudflare Free 하루 10만
4. VWorld 키 한도(미확인)
5. Lambda 동시 실행 1000(사실상 여유)

리미터를 올리면 문제는 해결되지 않고 다음 병목(하루 10만, VWorld 키 한도)으로 옮겨 간다.
