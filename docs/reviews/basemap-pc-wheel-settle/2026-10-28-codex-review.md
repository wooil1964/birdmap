## 2. 300~1000ms 휠 조작

12회 휠, 2개 해상도, 300·450·600·800·1000·1500ms의 12개 조합을 실제 Chrome과 Leaflet 1.9.3에서 시험했다. 대조군은 dc57e98 및 최신 main 각각 800·1000ms × 두 해상도, 총 8개다.

|---|---|---:|---:|---|

| 1920×1080 | 300·450·600·800·1000ms 각각 | 85 / 133 | 0 | VWorld ready |
| 1366×768 | 1500ms | 184 / 208 | 28 | OSM, 잠금 |

위 표는 Leaflet과 실제 기본지도 코드를 결합한 격리 지도 시험이다. 최종판 12건은 모두 예외 0건이었다. 기존판·main 대조군 8건은 모두 429→OSM이었고, 1920 대조군 4건은 `_fadeAnimated` 예외도 각각 재현했다.

1920의 Claude 측정 94건은 이 환경에서 재현되지 않았다. 전체 앱에서도 85건이므로 최소 지도 구성 차이만으로 설명할 수 없다. OS·Chrome·타일 배치·입력 시점 차이 가능성이 있으나 정확한 원인은 미확정이다. 요청 억제와 VWorld 유지라는 결론은 일치한다.

**유지 범위는 제한적이다.** 실제 앱 1920에서 같은 60초 창을 유지한 채 600ms × 12회 → 2초 휴식 → 같은 조작을 반복했다. 첫 조작은 초기 포함 169건·429 없음·VWorld였으나, 두 번째 조작에서 누적 209건·429 29건·OSM이 됐다(전체 약 20.3초). 전환 뒤 추가 요청은 0건, 예외 0건이었다. 따라서 빠른 조작도 반복하거나 이미 요청 예산을 사용한 경우에는 전환된다. 문제를 1500ms 이상 조작만의 한계로 설명하면 범위를 과소평가한다.

## 3. 1500ms의 429 위험

요청 억제가 적용되지 않는 간격에서는 매 레벨을 로드해 제한에 도달했다. OSM 전환, 잠금, 추가 요청 중단, 복귀 예약은 정상이다. 이 제한 자체는 이번 클라이언트 개선의 잔여 한계로 수용할 수 있으나, 다음 조건을 붙인다.

- VWorld 유지 보장을 단일 시험·리미터 여유가 있는 조건으로 제한해 설명한다.
- 1500ms뿐 아니라 빠른 조작의 반복, 팬, 공유 IP·전역 예산 소진도 같은 한계에 포함한다.
- 아래 복귀 이력 및 배치 경계 문제를 보완한 뒤 검증한다.

클라이언트가 모든 429를 없애려면 대기·요청 예산 관리 같은 다른 절충이 필요하다. 리미터·캐시를 바꾸지 않는 조건에서 **현재 방식으로 모든 정상 조작의 429를 보장할 수 없다는 것**과 **클라이언트에서는 원천적으로 어떤 개선도 불가능하다는 것**은 구분해야 한다. 후자는 이 시험으로 입증되지 않는다.

## 4. 성공 1개인 부분 복구 — P2 보완 권고

[기본지도 565~567행](https://github.com/wooil1964/birdmap/blob/fa2d9424c7ac59b45cf5dc1b05af29720143ffbe/assets/birdmap-basemap.js#L565)과 [오버레이 488~490행](https://github.com/wooil1964/birdmap/blob/fa2d9424c7ac59b45cf5dc1b05af29720143ffbe/assets/birdmap-basemap.js#L488)은 배치 성공이 1개 이상이면 이력을 지운다.

독립 VM 상태 시험에서 복귀 시도 → 1개 성공·나머지 취소 → 배치 완료 시 `recoveryAttempts=0`, OSM 배경 제거, `ready`가 됐다. 이어 다시 실패시키면 60초로 돌아갔다. 이 순서를 6회 반복해 매번 60초였으며, 4회 상한에 도달하지 않았다. 성공 1개·실패 2개의 실제 부분 배치도 `partial_error`이면서 이력을 초기화했다. 성공 1개·실패 23개는 장애로 판정해 120초를 유지하는 대조 결과도 확인했다.

이는 A의 성공 0개 문제와는 별개인 의도된 현재 정책이다. 다만 단 한 타일의 성공은 화면 복구 또는 지속적인 정상 상태의 충분한 근거가 아니다. 부분 성공을 끼우는 간헐 장애에서 백오프가 짧아지고, 부족한 화면 복구 상태에서도 배경을 제거할 수 있다. **표시 가능 판단과 안정 복구에 따른 이력 초기화 기준을 분리할 것을 권고한다.** 현재 뷰의 필요한 타일·취소 여부 또는 일정한 성공 지속 조건으로 판단해야 하며, 임의의 고정 타일 개수만 올리는 방식은 저배율·경계 화면을 함께 검토해야 한다.

취소 시나리오는 결정적인 VM 상태 재현이다. 대형 PC에서 같은 부분 복구가 자연 발생하는 빈도를 측정한 결과로 해석해서는 안 된다.

## 5. 지연 장애 전환과 다음 배치 — P2 보완 권고

[현재성 검사 228~233행](https://github.com/wooil1964/birdmap/blob/fa2d9424c7ac59b45cf5dc1b05af29720143ffbe/assets/birdmap-basemap.js#L228)은 레이어와 generation만 검사한다. [537행](https://github.com/wooil1964/birdmap/blob/fa2d9424c7ac59b45cf5dc1b05af29720143ffbe/assets/birdmap-basemap.js#L537), [561행](https://github.com/wooil1964/birdmap/blob/fa2d9424c7ac59b45cf5dc1b05af29720143ffbe/assets/birdmap-basemap.js#L561) 및 오버레이 465·485행의 지연 콜백에는 배치 식별자가 없다.

실제 Chrome·Leaflet 재현:

1. 초기 24장을 정상 로드한다.
2. 다음 뷰에서 11장 성공·13장 실패로 장애 판정을 예약한다.
3. 시험용 `layer.once('load')` 리스너가 `map.setView()`를 호출해 동일 레이어의 새 배치를 연다. 새 배치는 `loading/errors=0`이며 24장 모두 200 응답을 예정한다.
4. 이전 `later()`가 실행돼 새 배치를 제거한다. 최종 상태는 `OSM/tile_error/locked/errors=0`, 예외는 0건이다.

VM에서는 기본지도와 하이브리드 오버레이 모두 같은 문제를 확인했고, 교체된 레이어에 대한 기존 generation 보호는 정상임도 확인했다. 따라서 기존 시험의 '제거·교체한 레이어의 늦은 이벤트 무시'만으로 이 경계를 검증할 수 없다.

현재 앱에는 위와 같은 추가 VWorld `load` 리스너가 없으므로 **현재 제품에서 동기 순서가 자연 발생한다고 확정하지 않는다.** 입력 태스크와 타이머의 경쟁 빈도도 측정하지 않았다. 입증한 것은 가능한 Leaflet 순서에서 새 배치를 보호하지 못한다는 점이다. 배치 토큰을 캡처하고 새 `loading`에서 갱신해, 실행 시 여전히 같은 장애 배치인지 검사하는 보완 및 기본지도·오버레이 회귀 시험을 권고한다.

기본지도 장애 시험에서 외부 정적 캐시 696건을 제공하고, 기타 HTTP 2432건을 차단했다. Worker URL 요청 4950건은 모두 CDP 모의 응답 대상으로 처리했으며 원격 전송하지 않았다.

기존 하네스의 장애·취소·복귀·경계 화면 시나리오를 재사용하되 외부 요청 차단을 추가했다. 단위 시험 통과와 별도로, 위의 추가 시험은 현재 취약 동작을 관측하고 assertion으로 확인한 것이다. 추가 시험의 정상 종료를 해당 정책이 안전하다는 의미로 해석하지 않는다.

## 7. 최신 main 통합

최신 main의 추가 4개 커밋은 날씨·조석 자동 생성 JSON 5개만 변경했다. 브랜치의 수정 코드·시험·보고서 4개와 파일 교집합은 0이다. 기본지도 코드, 시험 파일, CI 설정, Leaflet 버전은 main에서 추가 변경되지 않았다.

실제 Git 병합 없이 main 스냅샷에 브랜치의 최종 4개 파일을 반영한 가상 통합본을 시험했다. 관련 코드·시험의 텍스트 충돌은 없으며, 통합 시험 결과는 위 표에 기록했다. main이 이후 바뀌면 이 판정의 기준도 다시 확인해야 한다.

첫 Windows 시험에서는 `test_weekly_recommendation.mjs`가 Python의 cp949 출력을 UTF-8로 읽어 1개 실패했다. `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`인 시험 환경에서 재검증했다. 저장소 코드를 수정한 해결이 아니며 JSON 한글 손상도 없었다. 이 환경 문제는 기본지도 수정의 회귀와 구분한다.
