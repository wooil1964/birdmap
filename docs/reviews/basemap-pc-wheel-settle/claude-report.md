## 1. 요약

PC에서 마우스 휠로 빠르게 반복해 확대·축소하면 VWorld가 OSM으로 바뀌는 문제의 원인은, 휠 한 번마다 화면 전체 타일을 새로 요청해 타일 Worker의 요청 제한(429)에 걸리는 것이었다. 429는 페이지에서 실제 장애와 똑같이 처리되어 OSM으로 전환되었다.

수정 후 로컬 모의 환경(Worker 리미터 60초 180건을 엄격히 흉내)에서 휠 간격 300~1000ms, 화면 1366×768·1920×1080 모두 VWorld가 유지된다. 단일 휠 줌의 응답성과 모바일 핀치 동작은 수정 전과 같다. 1차 수정에 대해 Codex가 지적한 결함 3건(복귀 이력 초기화 오류, 응답 순서에 따른 판정 불일치, Leaflet 내부 예외)은 dc57e98에서 각각 재현한 뒤 2차 수정에서 해결했다.

해결하지 못한 한계: 1.2초 이상 간격으로 오래 계속 확대·축소(또는 팬)하면 지금도 429 → OSM 전환이 생긴다. 리미터 크기가 PC 한 화면 타일 수에 비해 작아서이며, 리미터·캐시 정책을 바꾸지 않는 조건에서는 클라이언트만으로 막을 수 없다(9장).

## 2. 원인 조사 (10/27, 실운영 읽기 전용 재현)

방법: 로컬 헤드리스 Chrome을 CDP로 조작해 실제 운영 페이지에 실제 휠·핀치 입력을 보내고, 타일 요청의 응답 상태·헤더를 기록했다(설정·코드 주입 없음). 회당 약 700타일이 운영 Worker에 요청되었으므로 반복하지 않았다.

| 시나리오 | 입력 | 타일 요청 | 고유 타일 | 429 | 결과 |
|---|---|---|---|---|---|
| PC 빠른 휠 1회차 (1440×900) | 0.6초 간격 21회 | 651 | 215 | 5 | 13.1초에 OSM, 60.0초 뒤 복귀 |
| PC 빠른 휠 2회차 | 0.6초 간격 23회 | 702 | 215 | 6 | 14.6초에 OSM, 60.0초 뒤 복귀 |
| 모바일 핀치 (390×844) | 0.6초 간격 30회 | 404 | 151 | 0 | VWorld 유지 |
| PC 느린 휠 | 3초 간격 6회 | 160 | 108 | 0 | VWorld 유지 |

**확정**
- 실패는 Worker 자체 `429 tile_rate_limited`였다(`X-Tile-Upstream` 없음 = upstream 실패 아님, 응답 86~105ms, cf-ray 콜로 HKG).
- Chrome ORB가 429(text/plain + nosniff)를 막아 페이지·콘솔에서는 상태가 보이지 않는다(`net::ERR_BLOCKED_BY_ORB`, 원본 상태는 CDP `responseReceivedExtraInfo`로만 확인).
- 429가 정상 타일(약 220ms)보다 빨리 와서, 묶음 시작 시 실패 3건이 먼저 쌓여 즉시 `tile_error` → VWorld 레이어 제거 → OSM. 흐린 과정이 없는 이유는 확대된 이전 타일을 가진 레이어가 통째로 빠지기 때문이다.
- 휠 한 번이 약 290ms(입력 대기 40ms + 애니메이션 250ms)라, 0.5~0.7초 간격 반복이 매번 '단독 줌'으로 판정되어 화면 전체(1440×900 약 31장)를 요청했다.
- Worker `Cache-Control: no-store` 때문에 다시 본 타일도 다시 받는다(702요청 중 고유 215장).
- 요청 취소는 장애로 오인되지 않는다(Leaflet 1.9.3이 취소 타일 오류를 거름, 취소 28건 중 오류 집계 0건).

**추정**
- 리미터 시행이 근사·지연이다: 문서상 IP당 180·전역 300(위치별)인데 실측은 60초 창 약 680건째에 시작했다. 그래서 증상이 "항상"이 아니라 "자주" 나타난다.
- IP·전역 리미터는 응답이 같아 어느 쪽인지 구분할 수 없다. 전역이라면 같은 콜로의 다른 사용자도 함께 OSM이 될 수 있다.

**미확인**: 실배포 리미터 값 직접 조회, Workers 일일 사용량, CloudWatch·Cloudflare 지표(토큰 필요).

## 3. 1차 수정 (b3e1061, dc57e98)

- 휠·버튼 연속 줌 판정 대기 `ZOOM_SETTLE_MS` 200 → 400ms. 핀치가 끝날 때(Leaflet이 `zoomanim`에 `noUpdate`를 붙임)는 항상 즉시 로드.
- 마지막으로 로딩 중이던 타일이 줌으로 취소(`_abortLoading`)되거나 팬으로 제거(`_removeTile`)되면 Leaflet이 `load`를 쏘지 않아 묶음이 열린 채 12초 뒤 `tile_timeout`으로 OSM이 되던 잠재 버그 수정(main에서 재현: 타일 1.5초 조건에서 축소 직후 재확대). 남은 로드가 없으면 묶음을 닫는다.
- 자동 복귀: 60초 1회(세션당) → 60·120·240·480초, 로드 성공 시 초기화.
- OSM에서 돌아올 때 첫 VWorld 묶음이 로드될 때까지 OSM을 아래에 유지(빈 화면 방지).

## 4. Codex 검증 지적사항과 2차 조치 (1371691)

모든 결함은 수정 전 커밋 dc57e98에서 Chrome 또는 단위 시험으로 먼저 재현했다.

### A. 복귀 이력 초기화 오류 — 해결
- 원인: 성공 타일이 0개인 취소 배치도 '로드 완료'로 처리해 백오프 이력을 지웠다.
- 조치: 실제 로드된 타일이 1개 이상인 배치에서만 레이어를 '표시됨'(OSM 제거 가능)으로 바꾸고 이력을 초기화한다. 빈 배치는 둘 다 그대로 두고 12초 타이머만 정리한다. 하이브리드 겹침 레이어도 같다(빈 배치는 'ready'가 아니라 'loading').
- 확인: 복귀 시도의 첫 배치가 취소되면 시도 횟수 1 유지, 이어서 실패하면 다음 대기는 120초(60초로 돌아가지 않음). 복귀 시도 중 확대·축소·팬 후 성공하면 횟수 0(단위 + Chrome `recovery_attempt_with_zoom_and_pan`).

### B. 응답 순서에 따른 판정 불일치 — 해결
- 재현(dc57e98): 같은 소수 실패(5장 중 1장, 502)가 오류 먼저 도착이면 OSM, 성공 먼저 도착이면 VWorld 유지.
- 조치: `outage(failed, loaded, unanswered, shown)`가 개수만으로 판정한다.
  - 실패 ≥ 3이고 (성공 + 아직 응답 없는 타일)보다 많으면 실패.
  - 아직 아무것도 표시하지 못한 레이어가 실패만 받으면 실패.
  - 응답 없는 타일을 성공 가능성으로 세므로, 배치가 끝나기 전에 내리는 판정은 끝나도 바뀌지 않는 경우에만 나온다.
- 확인: 24장 배치에서 실패 3·11장은 오류 먼저·성공 먼저·섞임 세 순서 모두 VWorld 유지(partial), 13·18·24장은 세 순서 모두 OSM. Chrome에서도 소수·다수 × 두 순서 4개 시나리오 통과.
- 판정 시간(로컬, dc57e98 → 1371691): 전체 502 86 → 87ms, 다수 502 + 나머지 무응답 89 → 86ms, 소수 502(5/24) + 나머지 무응답 82ms → 12.0초(12초 마감에서 판정, 9장 참고).

### C. Leaflet 내부 예외 — 해결
- 재현(dc57e98): 다수 실패 + 성공 먼저 도착에서 `Uncaught TypeError: Cannot read properties of null (reading '_fadeAnimated')`. 원인은 Leaflet `GridLayer._tileReady`가 `load`를 쏜 뒤 `this._map`을 계속 읽는데, `load` 처리기 안에서 레이어를 제거한 것.
- 조치: 장애 전환을 `later()`로 다음 턴에 실행하고, 실행 시 같은 레이어·세대인지 다시 확인한다.
- 확인: Chrome 시험 하네스가 처리되지 않은 페이지 예외를 실패로 처리하도록 바꿈. dc57e98 예외 2건 → 1371691 0건. 단위 시험에서 자기 이벤트 처리 중에는 레이어가 지도에 남아 있고, 제거된 레이어의 늦은 이벤트(tileerror·tileload·load·loading·tileabort)는 상태·타이머를 바꾸지 않음을 확인.

### 800ms 이상 휠 간격 — 1000ms까지 해결, 그 이상은 한계
- 재현(dc57e98): 800·1000ms에서 감소 없음, 429 후 OSM(Codex 측정 1366×768 183→183건, 1920×1080 526→526건).
- 비교 검토:
  - 고정 대기 1000ms 이상 연장: 지시에 따라 채택하지 않음(짧은 연속 조작 끝까지 느려짐).
  - 클라이언트 요청량 제한: 채택하지 않음. 실제 리미터 상태(IP 공유, 근사 시행)를 알 수 없고, 명목값 180건에 맞추면 1920×1080에서 1분에 약 4화면만 선명해진다.
  - **연속 조작 상태 관리: 채택.** 이전 줌이 끝나고 900ms 안에 시작한 줌은 같은 연속 조작으로 보고 요청하지 않는다. 멈추면 최근 간격 × 1.25(400~900ms)만큼 기다려 최종 레벨만 로드한다. 단독 줌, 핀치 끝, 검색 결과로 이동한 직후의 줌은 즉시 로드한다(이동은 연속 조작 시계에 넣지 않음).
- 결과는 6장 표.

## 7. 확인된 사실과 미확인 사항

**확인됨 (로컬 시험 또는 실운영 읽기 전용 재현)**
- 실운영 PC 빠른 휠 OSM 전환의 원인은 Worker 429 (2회 재현, 원본 상태 확인).
- 2차 코드에서 300~1000ms 휠 간격은 리미터 모의 하에서 VWorld 유지 (1366·1920).
- 단일 줌 응답성·모바일 핀치 요청량은 수정 전과 같음 (핀치 103 ↔ 105타일).
- Codex 지적 A·B·C는 dc57e98에서 재현되고 1371691에서 해소됨.
- 실제 장애(502·끊김·무응답·429 폭주)에서 OSM 전환 유지, 백오프 순서와 초기화.
- 처리되지 않은 JavaScript 예외 0건 (장애 시험·측정 전체).

**미확인**

## 8. 잔여 위험과 기술적 한계

1. **느린 연속 조작의 429 (한계)**: 1.2초 이상 간격의 줌과 팬은 매번 한 화면을 로드한다. 리미터가 180건이면 1분에 화면을 바꿀 수 있는 횟수는 1366에서 약 7번, 1920에서 약 4번이다. 실운영에서 관측된 시행 지점(약 680건)으로도 1920은 약 15번이다. 이 범위의 429를 클라이언트에서 막으려면 사용자가 멈춘 뒤에도 지도를 오래 흐리게 둬야 해서 실용적이지 않다. 429가 나면 OSM 전환과 복귀는 정상 동작하며, 전환을 억제하지 않았다. 근본 대책(리미터 크기, 캐시 정책)은 이번 작업 조건 밖이다.
2. **일부 실패 + 다수 무응답에서 판정 지연**: 순서 무관 판정의 대가로 OSM 전환이 12초 마감까지 늦어질 수 있다(이전 약 0.1초). 실운영 Worker는 8초 안에 502로 응답하므로 실제로는 약 8초가 예상된다(미확인).
3. **연속 조작 판정**: 0.9초 안에 다시 줌하면 연속으로 보므로 그 줌은 최대 0.9초(+타일 시간) 늦게 선명해진다.
4. **Leaflet 1.9.3 내부 의존 증가**: `_tiles`, `_loading`, `_noTilesToLoad`, `_abortLoading`, `_removeTile`. CI의 `wheel_burst_skips_levels` 시나리오가 이 함수들의 존재를 검사한다. 업그레이드 시 재검증 필요.
5. **CI 시간**: 장애 시험 단계가 로컬 기준 약 11분(새 시나리오로 약 2분 증가). CI 20분 제한 안에서 여유가 줄었다.
