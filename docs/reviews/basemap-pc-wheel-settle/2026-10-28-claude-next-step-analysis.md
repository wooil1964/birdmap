## 1. 결론 요약

- 남은 429는 두 종류다.
  - (가) 세션 초반 불규칙한 휠 입력에서 생기는 **중간 화면 누수**: 낭비이며 클라이언트에서 쉽게 줄일 수 있다.
  - (나) 휴식을 낀 반복 조작에서 생기는 **정상 화면 갱신의 누적 비용**: 낭비가 아니라, 명목 리미터가 PC 화면 갱신 몇 번만 허용하는 구조에서 나온다.
- 1920×1080에서는 중간 누수가 전혀 없어도 "초기 화면 + 첫 줌 화면 + 최종 화면"만으로 엄격 모의(60초 180건)를 넘을 수 있다. Codex 측정: 600±150ms에서 84 + 54 + 54 = 192건, 최종 화면 12장이 429.
- 그래서 클라이언트 수정만으로는 명목 제한 아래에서 정상적인 PC 사용을 보장할 수 없다. 남은 질문은 "실제 운영 Worker가 어떤 제한을 어떻게 시행하는가"이고, 이것이 다음 결정을 좌우한다.
- **권고: C. Worker 제한 정책에 대한 별도 조사(읽기 전용부터).** 4차 클라이언트 코드는 C의 결과를 본 뒤 범위를 정한다. 다만 아래 B1(초반 누수 차단)은 작고 부작용이 거의 없어서, C 결과와 관계없이 다음 코드 수정 때 함께 넣을 후보로 둔다.

## 2. 현재 문제의 정확한 원인

### 2.1 화면당 비용 (확정, 로컬 모의 측정)
타일은 200ms 응답에 `no-store`, 입력은 3회 확대·3회 축소 반복이다.

| 항목 | 1366×768 | 1920×1080 |
|---|---|---|
| 초기 요청 (첫 화면 + 시험용 z11 이동) | 33 | 84 |
| 휴식 뒤 첫 단독 줌 1화면 | 24~28 | 40~54 |
| 연속 조작이 끝난 뒤 최종 1화면 | 24~28 | 40~54 |
| 중간 누수 1회 | 24 | 40 |

명목 IP 제한 180건/60초는 1366에서 약 6~7화면, 1920에서 약 3~4화면이다. 1920은 초기 요청만으로 그중 절반 가까이를 쓴다.

### 2.2 (가) 초반 불규칙 입력의 중간 화면 — 원인 확정
- 조건(Codex): 입력 간격 350·350·850·600·600·600ms 반복, 15초.
- 첫 두 입력은 줌 사이 틈이 약 90ms다. 이때 리듬 기록에는 짧은 틈만 있어서 정착 대기가 최소값 400ms(= 1.25 × 기록 최댓값, 최소 400)로 잡힌다. 다음 850ms 입력의 틈은 약 560ms라 대기가 먼저 끝나고, 화면 전체를 요청한 직후 다음 줌이 시작된다.
- 위치: `assets/birdmap-basemap.js` 376~383행(`_animateZoom`의 연속 조작 판정과 `_restMs` 계산).
- 최근 8개 틈을 기억하는 방식은 기록이 쌓인 뒤에는 잘 맞는다. 하지만 세션 초반처럼 아직 관측하지 못한 더 긴 틈은 예측할 수 없다.
- 이번 재현(r3): 1366 80건(1.5초에 중간 24), 1920 139건(1.5초에 중간 40) → 15.7초 OSM. Codex 수치(80 / 139, 15.771초)와 같다.

### 2.3 (나) 휴식을 낀 반복 — 원인 확정

- 반복마다 정확히 두 화면을 쓴다.
  - 휴식 뒤 첫 휠은 직전 줌 끝으로부터 0.9초가 넘어 단독 줌으로 판정되고, 줌 시작과 함께 한 화면을 즉시 로드한다. 이는 단일 줌 즉시 반응을 지키기 위한 설계다.
  - 멈춘 뒤 최종 한 화면을 로드한다.
- 이번 재현(r3, 정확한 2초): 1366 25.1초, 1920 8.9초 첫 429 → OSM. Codex 25.219초 / 8.861초와 같다.

### 2.4 Worker 제한 (코드·기록 확정, 시행 방식 미확인)
- `vworld-tiles/src/worker.mjs` 232~233행: IP 리미터(`CLIENT_TILE_LIMITER`)를 먼저, 전역 리미터(`GLOBAL_TILE_LIMITER`)를 그다음에 검사하고, 둘 다 같은 `429 tile_rate_limited`를 돌려준다. 응답만으로는 어느 쪽이 거절했는지 알 수 없다.

## 5. 권장 해결 방법과 선택 이유

**권고: C. Worker 제한 정책에 대한 별도 조사(읽기 전용부터)**

1. 남은 실패의 지배 요인은 낭비가 아니라 정상 화면 갱신 비용 대비 명목 제한의 크기다. 1920에서 누수 0건이어도 초기 + 2화면이 180을 넘는다(Codex 192건).
2. 클라이언트 최소 수정(B)은 효과가 제한적이다. B1은 초반 누수만 없애고, B2는 1366 반복은 통과시키지만 1920은 실패 시점을 8.9초에서 16.4초로 미룰 뿐이다. 게다가 B2는 사용자가 자주 하는 "줌 → 2초 보고 → 줌"을 약 0.65초 늦춘다. 단일 줌 반응성을 중요한 기준으로 삼으라는 원칙에 비춰 근거 없이 넣기 어렵다.
3. 실제 운영 시행이 미확인이다. 시행이 명목값 그대로라면 B를 넣어도 1920 PC 사용은 자주 429가 난다. 반대로 실제 시행이 충분히 관대하다면 3차 코드(A)로 충분할 수 있다. C의 결과가 A와 B 중 무엇이 필요한지 정한다.
4. C의 첫 단계는 읽기 전용이라 운영 위험이 없다.

**권고하지 않는 것:** 엄격 모의 통과만을 위한 요청 예산 강제(예산을 넘으면 선명화를 미뤄 흐린 지도를 오래 유지). 1920에서 1분에 3~4화면으로 묶어 정상 사용성을 크게 해친다.

**C 결과에 따른 다음 단계(제안)**
- 실제 시행이 명목값보다 충분히 관대하고 운영 429가 드물다 → A(3차 유지 후 운영 반영 검토, B1만 추가 검토).
- 명목값 그대로 시행되고 운영에서도 429가 잦다 → 제한값 재산정이나 브라우저 캐시 허용 여부를 정책으로 결정(VWorld 약관·비용 확인 후 별도 승인). 클라이언트는 B1과 필요하면 B2를 보완책으로 둔다.

## 6. 추가 수정이 필요한 정확한 범위 (승인 후, 지금은 구현하지 않음)

- **C(조사, 코드 변경 없음)**
  1. 배포된 Worker의 binding 설정 읽기: 대시보드의 Worker 설정, 또는 읽기 권한만 가진 단기 토큰으로 스크립트 설정 조회. 리미터 두 개의 limit·period와 README 값을 대조한다.
  2. 운영 지표 읽기: Workers 분석에서 요청 수와 하위 요청 수를 비교한다. 성공·502는 Lambda로 하위 요청을 1번 보내고, 429·403·404·503은 보내지 않는다. 그래서 차이로 거절 규모를 추정한다. AWS CloudWatch의 Lambda 호출 수로 교차 확인한다.
  3. VWorld 이용 약관(10/30 개정 포함)에서 캐시 허용 여부와 키별 호출 한도를 확인한다. 이전 기록상 캐시 허용은 미확인이다.
  4. 비용과 상한: Workers Free 하루 10만 요청, Lambda 요청·전송 비용, 제한 상향 시 남용 최악 시나리오.
- **B1(채택 시)**: `assets/birdmap-basemap.js`의 `_restMs` 계산 1곳(약 382행). 기록이 3개 미만이면 `ZOOM_RUN_MS`. 시험은 컨트롤러 단위 1건(초반 대기), Chrome 장애 시험에 초반 불규칙 시나리오 1개(1366·1920) 추가.
- **B2(채택 시)**: `_animateZoom`의 단독 판정 경계(약 378행)와 후속 줌 분기 추가. 응답성 회귀 시험(직전 줌 2초 뒤 단일 줌)을 새 기준으로 정해야 한다.

## 7. 구현 시 발생할 수 있는 부작용

- B1: 세션 첫 연속 조작이 끝난 뒤 최종 선명화가 최대 0.9초(+타일 시간)로 늦어진다. 이후에는 지금과 같다.
- B2: 직전 줌 0.9~3초 뒤 줌의 선명화가 약 0.65초 늦어진다(측정 940~970ms). 버튼이나 키보드로 한 단계씩 줌하는 사용자도 같은 영향을 받는다.
- B 공통: 정착·단독 판정 경로가 늘어 2·3차에서 고친 복귀 판정·배치 보호와의 상호작용을 다시 확인해야 한다. 복귀 판정과 배치 번호는 건드리지 않는 범위로 한정해야 한다.
- C(정책 변경 시): 제한 상향은 비용과 남용 노출을 키운다. 브라우저 캐시 허용은 약관 확인이 먼저다.
