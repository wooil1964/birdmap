## 8. 복구 계획

**배포 전 기록**: main SHA(현재 f8f80af, 배포 직전 값으로 갱신), Pages 배포 식별자, 기상 Worker 현재 버전 ID·바인딩, D1 `sites` 229행 전체 스냅샷·해시와 `system_state` mode·generation, 신규 ID 참조 0 확인.

**적용 순서**(승인 후): ① Worker 사이트 목록 확장(기존 secret·바인딩 보존) → 기존·신규 ID 응답 확인 ② D1 `append-registry.sql` 원자 추가 → 기존 229행 해시·신규 11행 확인 ③ Pages 공개 → 240곳·링크·기존 기능 확인. 각 단계에서 조건이 맞지 않으면 다음 단계로 가지 않는다.

**문제 시 복구**:
1. 먼저 **Pages 노출을 줄인다**: 배포 전 SHA로 복구(실제 병합 형태에 맞춰 revert 방식 결정)
2. D1에서 신규 ID를 참조한 제보·체크리스트, 신규 11행 해시, generation·NORMAL을 읽는다. **참조가 있거나 신규행이 바뀌었으면 D1 삭제와 Worker 축소를 중단**하고 데이터를 보존, 보고한다
3. 참조가 없을 때만 Worker를 기록한 이전 버전으로 복구하고 기존 ID 정상·신규 ID 미등록 응답 확인
4. D1은 `rollback-registry.sql`로 235~238·240~246만 단일 조건부 DELETE(참조·변경·세대 불일치 시 전체 거부, 시험으로 확인). 전체 DB 복원·초기화 금지
5. 기존 229행 해시·외래키·제보/공개/보호 상태와 Pages·Worker·공유·조석 생성물을 재확인. 생성물은 승인된 workflow로 재생성
