# PR #39 합성 승인 제보 검색 성능 측정

2026-10-21 KST. 운영 DB·실제 제보·배포를 사용하지 않았다. **아래는 로컬 workerd/Miniflare D1 실측이며 운영 Cloudflare 응답시간·CPU·과금·메모리 한도를 의미하지 않는다.**

## 측정 환경과 방법

- OS win32 10.0.19045, x64, CPU AMD Ryzen 5 5600 6-Core Processor, 논리 CPU 12개, RAM 16309.55 MiB. 호스트 OS의 일반 실행 환경이며 CPU 고정/배경 프로세스 통제는 하지 않았다.
- Node v24.18.0, Miniflare 5.20261006.1-alpha, workerd 1.20261006.1, compatibility date 2026-07-03. 계측 wrapper에만 nodejs_compat과 D1 진단 헤더를 추가했다.
- 실제 제품 public Worker와 native D1 binding, 현행 schema.sql + canonical core DDL을 사용했다. N마다 새 일회성 DB/isolate를 만들었다. 합성 승인 행 100/1,000/10,000개, 합성 공개 탐조지 229개, 공개/비공개 이름·민감종·가린 위치·번식 키워드가 섞인 결정적 fixture다. 실제 개인정보를 복사하지 않았다.
- q 없음 / 참새(정확히 50% 일치) / 없는합성종(0건), offset 0/20, 각 조건 첫 실행 1회와 연속 반복 20회. 동시성 1, 총 18조건×21회=378 검색 요청을 각 측정에서 수행했다. 조건은 고정 순서다. 첫 실행은 준비된 isolate에서 해당 query/offset의 첫 요청이며 콜드 스타트 수치가 아니다.
- 응답시간은 Node 호스트에서 request 시작부터 body JSON 소비까지의 wall time이다. DB 생성·시드·publication head·메모리 관측은 시간에서 제외했다. 프런트 사전/사후 head, 브라우저, 인터넷/TLS 지연은 이 수치에 포함되지 않는다.
- 시간/행 읽기는 inspector를 끈 측정, isolate heap은 별도 inspector 측정이다. 후자는 Runtime.getHeapUsage를 요청 전후에 읽고 각 조건 전 GC를 요청했다. idle workerd의 GC를 완료시키는 보조 head도 시간에서 제외했다. GC/inspector가 실행 조건을 바꾸므로 두 실행의 응답시간을 섞지 않았다.
- 힙은 제품 Worker isolate의 관측 시점 usedSize이며 wrapper/런타임 객체를 포함한다. 표의 값은 반복 요청 후 관측한 최댓값이다. 요청 실행 중 최고치나 운영 memory-limit 여유를 증명하지 않는다. 전체 workerd 프로세스 메모리와 Node 계측 프로세스 메모리는 아래에서 별도로 구분한다.
- 측정 당시 HEAD 91649629476296b43c7b4fd9613ed340e8114d9a. 서버 검색 소스는 이번 후속 수정에서 바꾸지 않았다. report-search.js SHA-256: 98e6b9106c67cbdf33abfaa1fdd883bc01f09aa646585560166102443066a0ec. raw 결과 두 실행과 각 요청의 실제 D1 metadata는 로컬 출력물에 보관했고 요약 JSON에도 원본 해시를 기록했다.

## 전체 프로세스 메모리 (별도 범위)

Windows에서 현재 Node의 직접 자식 workerd 한 개만 식별했다. 각 조건 시작/끝 시점의 WorkingSet64/PrivateMemorySize64 범위와 반복 요청 후 Node controller RSS 범위다. native workerd 수치는 D1·Worker·네이티브 런타임·할당자 보유 메모리 전체이며, Worker isolate의 JS 힙 또는 운영 Worker 제한과 비교할 수 없다. 조건마다 GC나 프로세스 재시작을 하지 않아 누적 보유량도 포함한다. 실행 중 peak를 샘플링한 수치가 아니다.

## 판단과 안전한 대안

관측된 rows_read는 N별로 465/2,265/20,265이며 q·offset·반복에 관계없이 같다. statement별로 reports가 2N, sites가 229, publication이 36행을 읽었다. 반복 요청에도 결과 캐시가 없으며 20행 응답이 20행 DB 읽기를 뜻하지 않는다. 승인 행 전체 조회·정렬·JS 공개 projection이 선형 비용의 원인이다. 10,000건에서는 별도 inspector 실행의 관측 heap도 약 47–55 MiB로 증가했으나 실행 중 peak나 운영 한도 충족은 확인하지 않았다.

검토한 대안:

1. 검색어 없는 경로만 COUNT+LIMIT/OFFSET와 페이지 행의 승인 부모 조회를 같은 primary batch에 넣기. 정렬 인덱스와 부모의 숨김/민감종/삭제/다단계 연결 보호까지 함께 증명해야 한다. 기존 정책과 다른 단순 SQL 페이지 조회를 넣지 않았다.
2. 공개 projection 전용 정규화 검색 인덱스. 모든 writer의 동의 철회·삭제·승인 취소·부모 위치 변경을 같은 transaction과 publication revision에 결합하고 정책 버전·backfill을 검증해야 한다. 마이그레이션/쓰기 경로 변경이 필요하다.
3. chunk 순회는 일부 중간 메모리를 줄일 수 있지만 정확한 검색 total과 snapshot을 유지하려면 여전히 전체 읽기가 필요하다. 별도 snapshot의 chunk나 낡은 권한 캐시는 허용하지 않는다.

**이번 후속 변경은 서버 검색 구조를 유지한다.** raw SQL LIKE로 비공개 이름·위치를 검색하거나 민감종 JS 판정·NFC 정규화·publication 검증을 우회하는 개선은 하지 않았다. 운영 성능 개선이 안전하게 입증되지 않은 상태에서 읽기량 감소를 주장하지 않는다.
